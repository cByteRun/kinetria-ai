## Клиентская обратная связь: узкий P0

### Обоснование включения в MVP

§2.2 ТЗ допускает клиентский контур при обосновании. Для группы, соединяющей продажи, закупки, проектирование, монтаж/ПНР, сервис и IT, проблема на объекте может быть следствием передачи данных между подразделениями. Внутренний сигнал показывает неудобство сотрудника; внешний — последствия для клиента. Их связка позволяет проверить, устраняет ли внутреннее улучшение источник повторных обращений, а не только закрывает отдельную заявку.

**Предлагаемый синтетический кейс:** клиент сообщает, что после ПНР невозможно найти актуальную инструкцию по системе. Сервис регистрирует сигнал и отвечает клиенту. Сотрудник создаёт связанное внутреннее предложение «проверять комплект исполнительной документации при передаче объекта»; руководитель назначает владельца, тот фиксирует изменение чек-листа. Клиент получает допустимое публичное резюме и оценивает результат. Повтор аналогичных сигналов проверяется на следующих объектах.

Дополнительная ценность — связь «внешний дефект → внутренний процесс → решение → оценка результата» с прослеживаемыми ID. **Многократное усиление ценности — гипотеза, не измеренный коэффициент.** Возвраты, повторные выезды, доверие клиента и издержки следует измерять на пилоте; данных для денежного обещания нет.

Граница P0: приглашённые клиенты одного пилотного направления, одна форма, собственный статус/публичный ответ, отдельный реестр в вебе, явная связь с внутренней инициативой и один опрос. Полноценный личный кабинет контрагентов, публичная лента, CRM сделок, договоры, продажи и общий доступ к знаниям в P0 не входят. Сначала портал; ветка Telegram использует тот же внешний сервис после проверки изоляции. Нельзя просто разрешить client существующий `submit_with_files`: его бизнес-права рассчитаны на сотрудника.

### Пользователи, данные и доступ

| Предлагаемая сущность | Назначение |
|---|---|
| `client_organizations`, `client_memberships` | Компания клиента, подтверждённый участник и активность; клиентская организация не равна подразделению Modus |
| `feedback_cases` | F-номер, организация/автор, необязательная проверенная ссылка на объект, категория сервиса, описание, статус, внутренний владелец, версия, ключ подачи, временные отметки |
| `feedback_messages` | Сообщение с `visibility=public/internal`; публичный ответ задаётся явно, копирование внутреннего текста запрещено по умолчанию |
| `feedback_attachments` | Приватные файлы внешнего кейса, лимиты MVP; доступ по внешнему кейсу, отдельный endpoint |
| `feedback_triage_memberships` | Явно назначенный employee-координатор внешних сигналов и разрешённая область; право не выдаётся всем сотрудникам |
| `feedback_case_events` | История внешнего кейса, действующий субъект и видимость события |
| `feedback_request_links` | Связь F-case ↔ R-request, тип причины/улучшения и автор решения о связи; many-to-many с уникальностью пары |
| `client_invitations` | Одноразовый хешированный токен, адресат, организация, срок и отзыв; токен не является постоянным доступом |

Клиент читает только **свои** F-кейсы и явно публичные сообщения/файлы. Общий просмотр всех заявок своей компании — отдельное будущее право, не default. Нет SELECT на requests, request_events, внутренние комментарии, оргструктуру или аналитику. Сервисный ответственный видит только назначенные внешние кейсы; руководитель — свою область; администратор — внешний реестр и маршруты. Для перехода F→R назначается employee-координатор в `feedback_triage_memberships`: он читает минимальную проекцию F в своей области (описание проблемы и разрешённые материалы, без контактов клиента и закрытых заметок). Это отдельное scoped право, не доступ всем сотрудникам. Точные области новых прав проверяются сервером и SQL. В UI это отдельный раздел «Клиентские сигналы», а не добавление внешних строк в общий список сотрудников.

В текущей схеме один `profiles.role`; P0 использует отдельную клиентскую учётную запись и membership, без скрытого совмещения employee/client. Множественные роли требуют отдельного проекта. Демороль client в enum не подтверждает членство в клиентской организации. Telegram-состояние разделяется по `(telegram_id, identity, contour)`, клиентская привязка — отдельным invitation-flow; действующий bridge клиентов запрещает и не должен открывать внутренние операции.

### Процесс и предлагаемые интерфейсы

1. Клиент открывает `/feedback`, проходит приглашение/подтверждение контакта. Публична только входная страница; обращение и просмотр требуют собственной подтверждённой сессии. Объект выбирается из разрешённых или остаётся непроверенным текстовым указанием до уточнения.
2. `POST /api/feedback/cases` валидирует вход, ограничивает частоту, проверяет организацию и idempotency key. Транзакция создаёт F-кейс, публичное событие и outbox; нет маршрута — отдельный резерв внешнего контура с владельцем.
3. `GET /api/feedback/cases/:id` и вложения возвращают только разрешённую публичную проекцию. UUID/номер не служит секретом доступа. Переходы: received → review → waiting_client / in_progress → resolved; ответ клиента возвращает review. Для resolved обязателен публичный итог.
4. Явно назначенный employee-координатор читает разрешённую минимальную проекцию F и вручную создаёт собственное R-предложение существующим `submit_with_files`; автор R — этот employee, а не клиент/handler. Handler/manager/admin запрашивают у координатора создание улучшения, но не вызывают подачу от чужого имени. Проектируемая команда `link_feedback_request` проверяет активное triage-membership, область F, авторство и доступ к R, уникальность пары; событие сохраняет действующего actor. Решение и ack в R проходят без изменения действующих employee-прав. Клиент получает ответ только в F. При отсутствии координатора сигнал остаётся в очереди с явным состоянием «нужна передача на улучшение». Наличие сервисного кейса не требует новой инициативы, если нет проблемы процесса.
5. Закрытие R-инициативы не закрывает все связанные F-кейсы автоматически. Владелец проверяет применимость решения к каждому клиенту, публикует безопасное резюме, клиент видит свой результат и может запросить повторное рассмотрение.
6. Терминальное событие с решением создаёт опрос. Внешний и внутренний реестры дают отдельные показатели, связь позволяет оценить повторные сигналы по процессу без раскрытия исходных текстов клиентам.

Защита: SQL-политики и доменные проверки в service bridge, серверные секреты, безопасная выдача файлов, Origin/CSRF для web-записи, квоты, redaction контактов, удаление/retention по согласованной политике. Антивирус/карантин и большие файлы — gate реального клиентского пилота; для демо только синтетические материалы. Внешним моделям не передаются реальные клиентские тексты без согласования.

**Приёмка P0:** клиент A создаёт F-кейс с файлом; B той же/другой организации не читает карточку/файл/события прямым API; повтор не создаёт второй F; сотрудник создаёт и связывает R; руководитель/ответственный фиксируют улучшение; клиент читает только опубликованный итог; отказ маршрута виден в резерве; внутренние поля не попадают в ответ/лог/уведомление. Лишь после этого портал называется работающим MVP.

<a id="nps-и-оценка-решения-p0"></a>

## NPS и оценка решения — P0

### Разные вопросы для разных целей

- **Сотрудник после содержательного решения:** «Насколько вы удовлетворены результатом рассмотрения?» — CSAT 1–5 + необязательный комментарий. Внутренний eNPS о работодателе не подменяется этим вопросом.
- **Клиент после завершённого сервисного кейса:** NPS 0–10 «Насколько вероятно, что вы порекомендуете ГК „Модус Трейд“ коллегам?» + причина. Дополнительно можно дать CSAT результата, но это отдельная метрика.
- Посещение портала без решения не запускает опрос результата. Если опрос проводится после опыта использования портала, его цель/когорта подписываются отдельно.

Текущее поле `sentiment` — оценка тональности текста, в том числе подсказанная AI. Это **не ответ пользователя, не удовлетворённость, не NPS** и не источник новых графиков.

### Предлагаемый механизм

`survey_campaigns` хранит тип, формулировку/версию вопроса, период и контур; `survey_invitations` — case/request, адресат, `resolution_version`, сроки, delivery-state, хеш одноразового токена; `survey_responses` — invitation, score, comment и responded_at. Уникальность `(contour, case_id, resolution_version, recipient_id, survey_type)` защищает повторную отправку, уникальность invitation — повторное принятие ответа.

В транзакции терминального перехода с непустым решением создаётся survey-event в outbox. Для сотрудника приглашение показывается после ознакомления либо отдельным уведомлением о решении; отказ оценивать не препятствует чтению/ack. Telegram получает подписанную/неугадываемую краткую ссылку или callback с серверной привязкой к invitation. Проверяются текущий субъект, срок, тип/диапазон ответа и одноразовость, а не только номер callback. Веб использует ту же серверную команду. Если Telegram не привязан, приглашение остаётся доступным в вебе.

Предлагаемая настройка P0: приглашение через 24 часа после результата, одно напоминание через 72 часа, срок 7 дней; значения согласуются, scheduler и outbox обязательны. Закрытие с мотивированным отказом тоже допускает CSAT, чтобы не отбирать только довольных. Повторное открытие проектируемого F-кейса отменяет ещё не отвеченное приглашение; повторное решение F создаёт новую версию, которую отчёт не смешивает с прежней без явного выбора когорты. Доставка не считается ответом. Действующие R-статусы терминальные, повторное открытие R этим P0 не добавляется; для R повторная invitation при том же результате запрещена.

### Виджет и формулы

`NPS = 100 × (ответы 9–10 − ответы 0–6) / все валидные ответы 0–10`. Ответы 7–8 входят в знаменатель. Например, из 10 ответов 6 промоутеров, 2 нейтральных, 2 критика: NPS = +40, не 40% удовлетворённых. При n=0 — «Нет ответов».

Виджет показывает NPS от −100 до +100, n, распределение, долю ответа `ответившие / приглашённые`, период, контур и версию вопроса. При малой выборке — явная пометка; рабочий порог отображения разрезов предлагается n≥10 и согласуется отдельно. CSAT: доля 4–5 / все валидные 1–5 и n, отдельно от NPS. Период основной когорты — дата решения, окно ответов фиксируется, иначе сравнение месяцев искажено поздними ответами.

Руководитель видит собственную область, админ — разрешённую общую; клиент — только свой ответ, без внутренних агрегатов. Комментарии доступны уполномоченным, не всему коллективу. Отрицательная оценка создаёт задачу разбора человеку, не изменяет решение и не обучает модель автоматически. В P0 нет кампаний сегментации и редактора произвольных опросов.

**Приёмка:** одна invitation на событие, повторы безопасны, чужой/истёкший токен и неправильная шкала отклоняются, ответ фиксируется один раз, отказ/нет Telegram/пустая выборка корректны; контрольный набор даёт +40; CSAT и sentiment не смешиваются.

## RAG и база успешных кейсов — P1

### Целесообразность

Требование §1.3/§2.7 уже частично закрывается объяснимой группировкой по категории/тегу. RAG нужен для похожих формулировок и повторного использования **проверенного** решения, а не ради демонстрации AI. На 20 синтетических карточках нельзя доказать качество семантического поиска или экономию. Сначала собрать подтверждённые кейсы, ручные связи повторов и контрольную выборку вопросов; затем сравнить lexical/tag baseline с RAG.

### Предлагаемый pipeline

`терминальная карточка с решением → проверка владельцем знаний → структурированная версия кейса → redaction → knowledge_cases/chunks → embeddings + lexical index → поиск с областью доступа → ссылки и проект рекомендации → подтверждение человеком`.

Источником истины остаётся БД. `memory.md` — воспроизводимый структурированный экспорт/артефакт знаний, а не бесконтрольно дописываемый файл в Git с клиентскими данными. Для каждого проверенного кейса: ID и версия источника, контур/ACL, категория, подразделение, оборудование/система, симптом, подтверждённая причина (либо «не установлена»), решение и шаги, ограничения применимости, факт/период проверки результата, проверяющий, reviewed_at, source IDs и срок пересмотра. Включать только reviewed кейсы с подтверждённой полезностью; один `implemented` недостаточен. Отказы могут храниться отдельно как ограничения, но не как успешные решения.

Векторный индекс (например, PostgreSQL с векторным расширением после выбора/проверки поддерживаемой версии) хранит `case_version`, `chunk_id`, `embedding_model/version`, category, contour, ACL, active/deleted. Фоновая идемпотентная индексация, переиндексация при смене модели, tombstone при удалении/отзыве прав. Нельзя полагаться на фильтрацию только после генерации: доступ проверяется до retrieval и перед выдачей источника.

При подаче: пользователь подтверждает категорию → система ищет в той же категории и доступном контуре → hybrid retrieval (лексика + embedding), затем ранжирование → максимум 3 похожих кейса с ID, кратким совпадением и ограничениями. Для слаботочки/ПНР учитываются модель оборудования, версия ПО и среда. Расширение за пределы категории — отдельное действие. LLM формирует «возможный вариант из R-…», не «решение принято». Отсутствие надёжного источника приводит к отказу от подсказки; ручная подача всегда остаётся.

Новый кейс не сливается со старым автоматически. `request_relations` хранит proposed/confirmed/rejected relation, автора подтверждения и основание; только человек подтверждает повтор и применимость решения. Это позволит считать уникальные внедрения и случаи повторного использования. Автоулучшение — контур обратной связи: применили → проверили → одобрили новую версию знаний. Нет самоперезаписи правил/промптов по одному ответу или негативному NPS.

Безопасность: тексты кейсов — недоверенные данные, prompt injection не даёт прав выполнять команды; отдельные ACL внешних/внутренних знаний, redaction, контроль логов, квот и стоимости. Клиент никогда не получает внутренний memory.md/embedding context. Ретенция исходника распространяется на экспорт и индекс.

**Предлагаемый эксперимент, не полученные результаты:** ≥30 размеченных новых запросов и достаточный согласованный корпус; precision@3 ≥80%, ни одной утечки в негативных ACL-тестах, доля полезных подсказок и latency/cost фиксируются. Сравнить с текущими тегами на одинаковой выборке. При отсутствии прироста/корпуса оставить текущую аналитику, RAG не делать блокером MVP.

IdeaRoute хранит reference, не копию цен/договоров | Адаптер read-only через согласованный HTTP-сервис/OData/выгрузку, по доступным возможностям конкретной конфигурации | Версия платформы/УТ, доработки, где реально ведётся объект, опубликованные API и сеть/VPN, GUID, объёмы/дельты/удаления, права на коммерческие поля, администратор и тестовая копия |

Прямого изменения остатков/цен в проекте нет |

### Общий контракт надёжности

Event envelope: `event_id`, `schema_version`, `origin`, `entity_id`, `entity_version`, `occurred_at`, `correlation_id`, минимальный payload. Outbox фиксируется вместе с доменным изменением, consumer хранит receipt по `(system,event_id)`, mapping — внешние ID и последняя версия. Retry с backoff, dead-letter после согласованного числа неудач, ручное переисполнение и сверка потерянных событий. Проверять подпись/секрет и replay, хранить credentials только на сервере, журналировать IDs/статус без чувствительных payload.

Источник истины: корпоративная система — оргструктура/master data; IdeaRoute — обращение, решение и ознакомление; Битрикс24 — выполнение связанной задачи. «Задача выполнена» создаёт событие/предложение перехода, но не автоматически публикует решение автору: ответственный проверяет и фиксирует итог в IdeaRoute. Изменения с origin и версией не отправляются по кругу. Недоступность 1С/Б24 не блокирует регистрацию и внутренний сценарий, но видна оператору как ожидающий обмен.

**Приёмка интеграций:** повтор события не создаёт второй task, увольнение отзывает назначение по утверждённому правилу, конфликт версии не затирает решение, временный отказ восстанавливается, входящий task done не закрывает R без содержательного решения. Доступный API, используемые scopes и стоимость сверяются с владельцами систем до реализации. Сейчас ни один из этих обменов не подключён.
