## Вывод

**Внутренний MVP убедителен по коду и покрывает шесть шагов §2.3. Готовность полного живого голосового показа и промышленного внедрения пока не доказана.** Работающий домен нельзя приравнивать к безотказной доставке, а синтетические метрики — к эффекту у заказчика. Клиентский портал — заглушка; NPS, RAG и корпоративные интеграции отсутствуют. Их архитектура теперь описана в [стратегических расширениях](STRATEGIC_EXTENSIONS.md), но реализация от этого не появилась.

Шансы на сильную защиту повышают единый реестр веба/бота, права на уровне SQL, резерв, обязательное решение и ознакомление автора. «Безоговорочное лидерство» и процент победы не выводятся из репозитория: нет официальной шкалы, материалов конкурентов и результатов пилота.

## Сквозная цепочка: что именно связано кодом

| Шаг и роль | Маршрут / функция / данные | Доказательство и предел |
|---|---|---|
| Вход сотрудника | `/auth/login` → `getProfile` → `/workspace/employee?view=new`; бот — link либо маркированный `/login` | Роль из активного профиля, не из URL. Синтетический вход демонстрирует реальные права |
| Голос/текст и файл | `bot.ts` → `api.ts:transcribe` → Groq → session draft; веб `prepareDraft` / ручная форма | Автор проверяет поля. Голос ≤120 с / 3 МиБ. Whisper подменён в локальном workflow |
| Подтверждение | Бот `submit` → `telegram_bridge` → `submit_with_files`; веб `submitRequest` → тот же RPC | requests + files + events + outbox в доменной транзакции; уникальность `(author_id, submission_key)` |
| Надёжный приём | `POST /api/telegram/webhook` → `telegram_enqueue` → ACK → `after` / `drainInbox` | ACK означает сохранённое задание, а не регистрацию карточки. При ошибке БД — 503 |
| Руководитель назначает | `assign` bridge → `review_request`, срок в той же транзакции; веб `updateRequest` | Область категории и активность назначения, версия против гонок; не балансировщик нагрузки |
| Нет маршрута → администратор | `/reserve`; веб `dashboard_action(assigned)` | Admin назначает из резерва руководителя, тот получает область категории. Admin не публикует решение |
| Ответственный уточняет и решает | `review/reply` → `review_request`; `review → clarification → review → in_progress → implemented/rejected/closed` | Вопрос, следующий шаг и итог обязательны на соответствующих переходах. Обновление и событие атомарны |
| Автор узнаёт результат | `deliverOutbox` → приватное уведомление → detail; веб `results/notifications`; `dashboard_action(acknowledged)` | Доставка, просмотр и ack — разные факты. Переназначенный теряет доступ; старые Telegram-копии не стираются |
| Руководитель/админ анализирует | `/workspace/{manager,handler,admin}?view=analytics` / `insights` → общие requests → `lib/insights.ts` | Источник тот же. Другая область не включается; данные обновляются по запросу/30-секундному refresh |

**Разрыва на уровне доменных функций не обнаружено.** Для заявления «полностью работает в целевой среде» доказательств недостаточно. Нет атомарной транзакции Telegram + PostgreSQL: внешнее сообщение иногда может повториться. Scheduler нужен при отсутствии новых updates; один успешный ручной `/deliver` не подтверждает расписание. Аналитика загружает набор через Data API без полноценной пагинации, поэтому полноту больших реестров нельзя обещать.

## Что проверено в этом аудите

Повторно выполнены с PASS: `check-telegram.mjs`, `check-telegram-api.mjs`, `check-telegram-webhook.mjs`, `check-telegram-inbox.mjs`, `check-telegram-delivery.mjs`, `check-telegram-demo.mjs`, `check-insights.mjs`. Это локальные проверки с имитациями транспортов/БД по устройству конкретного скрипта; 100 admissions в webhook-тесте не являются 100 RPS production.

Исторический SQL workflow читался как доказательство устройства проверки: использует настоящую локальную PostgreSQL с ROLLBACK, но подменяет Telegram, Whisper и часть доставки. В этом аудите он повторно не запускался. Исторический [отчёт восстановления 13.11](VALIDATION.md#восстановление-production-telegram-13112026) фиксирует 7 завершённых updates, pending=0, HTTP 200 deliver и deployment READY; здесь эти наблюдения заново не снимались. R-067 — историческая доставка через API, не полный человеческий голосовой сценарий.

## Оценка по трём вопросам §6

1. **Бизнес-задача — сильная связь:** карточка сохраняет ответственность и итог при передаче между подразделениями. Для лидерства нужен хотя бы один наблюдаемый межотдельный кейс и замер потерь/ручной координации до пилота; сейчас эффект гипотетический.
2. **Работа на практике — сильный домен, неполная эксплуатационная приёмка:** закрытый цикл, резерв и запреты реализованы. Для убедительного показа — свежая запись полного живого прохода, проверка чужого файла/области и восстановления доставки.
3. **Развитие и интеграция — обоснованный путь:** клиентский сигнал связывается с внутренним улучшением, опрос оценивает результат; RAG и корпоративные обмены вынесены дальше. Для превосходства нужен согласованный минимальный контур и владелец процесса, а не количество слайдов о будущих функциях.

Клиентский P0 повышает потенциальную ценность, но расширяет поверхность доступа и может сорвать стабильность основного показа. Поэтому внутренний E2E — первый gate, клиент/NPS принимаются отдельно. Если они не готовы, защищаем честный внутренний MVP и показываем архитектуру расширения без заявления о работающем портале.
