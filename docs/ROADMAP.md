## 2. P0 — включаем в MVP для тендерного преимущества

Порядок зависимостей: **P0.1 внутренний живой цикл → P0.2 клиентская изоляция/сигнал → P0.3 опросы → P0.4 пакет защиты**. Реализация портала/NPS этим обновлением документации не выполняется. При нехватке времени показываем принятый Core, а незавершённые P0 честно оставляем планом.

### P0.1 Полировка и доказательство внутреннего цикла

- [ ] Пройти на целевом deployment настоящий голос → редактирование → файл → R-номер → тот же номер в вебе → руководитель/назначение/срок → ответственный/уточнение → ответ автора → решение → уведомление/ack → аналитика. Сохранить протокол версии, времени и ролей.
- [ ] Настроить регулярный `/api/telegram/deliver`; доказать восстановление временно неудачной доставки без нового webhook. Назначить владельца inbox/outbox и резерва.
- [ ] Проверить чужую карточку/историю/файл прямым запросом, отзыв назначения и конфликт версий. Пройти резерв и мотивированный отказ.
- [ ] Репетиция с отдельными идентичностями участников; не обещать массовый QR-вход на восемь общих аккаунтов. Голос при отказе провайдера заменяется ручным текстом с явным пояснением.
- [ ] Зафиксировать точные подписи метрик и стартовые значения; подтвердить полноту демовыборки в пределах Data API.

**Готово:** один воспроизводимый живой сценарий и сценарий восстановления, отрицательные проверки доступа, журнал с фактическими результатами; нет утверждений о неизмеренных RPS/экономии.

### P0.2 Узкий клиентский портал фидбеков

**Обоснование §2.2:** сигнал клиента на объекте/сервисе связываем с внутренним улучшением передачи работ между продажами, закупками, проектированием, монтажом/ПНР, сервисом и IT. Это проверяет, доходит ли внутреннее решение до внешнего результата. Усиление ценности — проверяемая гипотеза, без обещания кратной экономии.

- [ ] Клиентские membership/invitation, отдельные F-кейсы, файлы/события и безопасная публичная проекция. Вход по приглашению; клиент видит только свои записи.
- [ ] Портал: подача → статус → публичный ответ; отдельный реестр/резерв во внутреннем дашборде.
- [ ] Scoped employee-координатор F→R и ручная проверяемая связь F-кейс ↔ собственная R-инициатива; решение внутреннего кейса не закрывает автоматически клиентский.
- [ ] Негативные проверки client A/B, внутренние записи и файлы недоступны, повтор подачи безопасен, секреты и внутренний текст не попадают в публичные ответы.
- [ ] Telegram-ветка клиента — после приёмки внешней модели доступа, на тех же контрактах. Для минимального P0 достаточно портала.

**Готово:** клиентский сигнал → связанное внутреннее улучшение → проверенное публичное резюме клиенту, на синтетических данных с доказанной изоляцией. [Модель/API/права](STRATEGIC_EXTENSIONS.md#клиентская-обратная-связь-узкий-p0).

### P0.3 Базовые NPS / CSAT

- [ ] CSAT 1–5 после решения сотруднику, NPS 0–10 после клиентского сервисного результата; не смешивать с sentiment.
- [ ] Версионированное приглашение из терминального события/outbox, проверка адресата/срока/одноразовости, веб и Telegram, отказ от ответа допустим.
- [ ] Виджет NPS с n, response rate, распределением, периодом и контуром; CSAT отдельным показателем, пустая/малая выборка обозначена.
- [ ] Пройти повторную доставку, чужой токен, повторный ответ, повторное открытие, отсутствие Telegram; проверить NPS +40 на контрольных 10 ответах.

**Готово:** реальный ответ на зарегистрированное решение отражается в правильном виджете, не создаёт дубли и не раскрывает чужие данные. [Механика](STRATEGIC_EXTENSIONS.md#nps-и-оценка-решения-p0).
