# Workspace: навигация, AI-сводки и голосовой черновик — 13.11.2026

Обновление сохраняет внутренний Closed-Loop: автор проверяет и редактирует карточку, затем отдельно регистрирует обращение. Голос не создаёт запись автоматически. Схема БД, RLS и матрица ролей не менялись.

## Фон и переходы

В исходном браузерном замере `html` имел прозрачный фон, а скрытая `.skip-link` в тёмной теме — светлый `rgb(238, 241, 248)`. Стили Workspace импортировались страницей, и его загрузочная граница заменяла целый экран. Эти места могли показывать светлую подложку при переходе; конкретный кадр исходного белого прямоугольника в автоматическом прогоне не воспроизведён, поэтому единственная первопричина не считается доказанной.

Фон и `color-scheme` закреплены на `html`/`body` в корневом stylesheet; loading использует `--panel`/`--text`. Стили Workspace перенесены из страницы в постоянный `app/workspace/layout.tsx`, без добавления всего CSS кабинета на лендинг. Каркас находится в `[role]/layout.tsx`, загрузочная граница — внутри него. Убрана анимация всего контейнера `.content`; skip-link обрезан вне `:focus-visible`, оставаясь доступным с клавиатуры. Не требуется отключать SSR. Все новые поверхности используют общие переменные синей/фиолетовой и светлой/тёмной темы.

## Композиция и Markdown

Знак бренда ведёт на `/`, текст IdeaRoute — на `?view=overview` текущей роли. Поисковая строка, язык, тема, палитра, профиль, выбор роли и уведомления используют общие высоту, радиус, границу и тематический фон. Шапка переносит элементы на узких экранах.

AI-сводка поддерживает заголовки, списки, выделение, цитаты, inline/fenced code, GFM-таблицы и чекбоксы. Сырой HTML не исполняется, опасные URL фильтрует react-markdown, внешние изображения не загружаются. Markdown остаётся в отдельном модуле, не требуя нового AI SDK или изменения существующего Groq-пайплайна.

## Голос: подключение и проверка

Новый маршрут: **POST `/api/voice/transcribe`**, multipart field `audio`. Требуются сессия сотрудника и same-origin запрос. Успех: `{ "text": "…" }`; ошибки — JSON с `error` и кодом HTTP. Поддержаны `audio/webm`, `audio/ogg`, `audio/mp4`, `audio/wav`; максимум 3 МиБ, интерфейс ограничивает запись двумя минутами. Сервер ограничивает фактически прочитанное тело, включая chunked upload. Расширение файла нормализуется сервером. Ключ не попадает в браузер.

В `.env.local` / окружении deployment:

```dotenv
GROQ_API_KEY=<существующий ключ Groq>
GROQ_WHISPER_MODEL=whisper-large-v3-turbo
AI_PROVIDER=groq
# GROQ_TEXT_MODEL — существующая модель AI-черновика проекта
```

Telegram и веб используют общий `lib/speech.ts`. `GROQ_API_KEY` и Whisper-модель уже были предусмотрены для Telegram; Telegram-токен для веб-записи не нужен. STT имеет таймаут 20 с, браузер — 30 с. Для AI-заполнения также нужны существующие Supabase и AI-настройки; если AI отключён, распознанный текст остаётся редактируемым описанием.

Проверка вручную:

1. Открыть сайт по HTTPS или localhost, войти сотрудником → новое обращение → «С помощью AI».
2. В пустом поле нажать микрофон, разрешить доступ. Видны таймер и индикатор записи. «Отмена» ничего не отправляет; на пределе времени запись переходит в прослушивание с отдельной отправкой.
3. Нажать «Отправить запись»: в чате остаётся аудиоплеер, затем транскрипт и ответ AI; справа заполняются тема, категория, тип, теги и предложение. Проверить и исправить карточку до регистрации.
4. Отказать микрофону или отключить сеть: отображается локализованная ошибка. После сетевой ошибки аудио сохраняется и доступен повтор распознавания без дублирования пузыря.
5. Уйти со страницы во время записи: микрофон освобождается; object URL очищаются при размонтировании/сбросе.

Клиентское аудио хранится только в памяти вкладки и передаётся Groq для транскрибации. Отдельный аудиофайл обращения в БД не сохраняется; автор регистрирует проверенное текстовое описание.

## Статусы, AI-темы и Telegram-сводка — 13.11.2026

- Степпер карточки использует общий `requestProgressIndex`: new → review → clarification → in_progress → result. Для implemented/rejected/closed все предыдущие этапы подсвечены независимо от наличия событий в истории. Это визуальная позиция жизненного цикла; фактическая история переходов не переписывается. Отдельного статуса «На проверке» в домене нет.
- В реестр добавлен самостоятельный блок смысловых AI-тем. Запуск явной кнопкой; периоды 7/30/90 дней. Сервер заново проверяет роль и выбирает только видимые по RLS проблемы за два равных периода до начала текущего часа UTC. Анализируется title/description, без привязки к категории или тегу. AI возвращает название и ID; сервер отклоняет неизвестные/повторные ID, пустые названия и группы меньше двух обращений. Один ID принадлежит максимум одной теме. Темы — гипотезы, не подтверждённые дубликаты.
- Тренд — сравнение количества в выбранном периоде с предшествующим равным периодом. Нажатие на тему ограничивает текущий реестр её ID за выбранный период; остальные фильтры продолжают действовать. Есть сброс темы и состояния ожидания/ошибки/пустого результата. Старый режим групп по категории/тегу сохранён отдельно.
- Next Data Cache хранит результат час. Ключ включает SHA-256 точного доступного набора текстов/ID/дат, модель, язык, период и часовую границу; повторное открытие не вызывает генерацию автоматически. При изменении доступа или данных старый результат не используется. Ограничение одного анализа — 200 проблем и 120 000 символов сериализованных данных; при превышении предлагается меньший период. На serverless фактическое сохранение кэша зависит от хостинга Next.js.
- Telegram: `lib/telegram/bot.ts` добавляет «✨ AI-сводка» администратору, ответственному и руководителю. `summary:<uuid>` проверяет роль и повторно читает detail через защищённый bridge. Общий сервис `lib/request-summary.ts` используется также веб-действием `summarizeRequest`; отправляются только поля обращения из белого списка. В Telegram используется обычный текст без parse_mode, поэтому HTML/Markdown не исполняются; транспорт уже делит длинный ответ. При ошибке AI доступны повтор и возврат к карточке. Реальная отправка сообщений при локальных проверках не выполнялась.
- Шапка от 1280 px: крошки слева, поиск/навигация по центру, системные контролы и единый профиль справа. В профиле — роль, смена аккаунта (когда доступна), настройки языка/темы/палитры и выход. На 1280–1439 px выбор палитры находится в профиле, язык и светлая/тёмная тема остаются в шапке. На 1280–1500 px скрыта визуальная подсказка Ctrl K, сочетание работает.
- Редактор категории администратора открыт сразу. В ручной форме выбран вариант Б: сохранён переключатель AI/ручного режима и удалена дублирующая кнопка AI; регистрация по-прежнему требует явного подтверждения автора.

## Сохранённые темы, Qvin и портал — 13.11.2026

Реализован цикл «выборка → AI-черновик → явное сохранение → общая тема» в вебе и Telegram. Это инструмент анализа повторяющихся сигналов Business Vision: тема не сливает обращения, не подтверждает общую причину и не наследует решение между авторами.

### Хранение и права

Миграция `20261113021538_registry_topics.sql` добавляет `topics` (`id`, `title`, необязательный `description`, `is_ai_generated`, `created_by`, `creator_role`, `created_at`) и many-to-many `topic_requests` с уникальной парой тема/обращение и внешними ключами. При удалении темы каскадно удаляются только связи. API проецирует связи как `ticketIds`, создателя как `createdBy` и `creatorRole`. Идентификатор черновика обеспечивает идемпотентность повторной отправки; изменение содержимого с тем же ID даёт конфликт.

`POST /api/topics`, `GET /api/topics`, `DELETE /api/topics/[id]` работают через общий `topic_service`. Telegram вызывает тот же сервис через namespace `topics` в доверенном `telegram_bridge`; профиль определяется по текущей привязке, роль/создатель не принимаются от клиента. Привилегированный код находится в `kinetria_private`, с фиксированным search_path, явными GRANT/REVOKE и проверкой активного профиля. Таблицы защищены RLS; прямые INSERT/UPDATE/DELETE для authenticated закрыты.

| Роль | Генерация/сохранение | Удаление |
|---|---|---|
| Ответственный (`handler`) | Только текущие назначения | Нет |
| Руководитель (`manager`) | Категории своего направления | Нет |
| Администратор (`admin`) | Общий реестр | Любая тема |
| Сотрудник, клиент | Нет | Нет |

Тема читается только если доступны **все** её обращения; частичная видимость не раскрывает чужие заголовки и счётчики. Изменение назначения влияет на доступ при следующем чтении. AI-тема требует минимум двух уникальных существующих доступных обращений; ручная тема — минимум одного. Сохранение проверяет каждую связь атомарно и блокирует смену назначения на время проверки. Пустые/вымышленные/недоступные ID отклоняются. Генератор получает только выбранные RLS-доступные записи и проверяет возвращённые ID; темы без записей не показываются. В свободном аналитическом диалоге Qvin усилено требование подтверждать повторяющиеся темы минимум двумя ID; это инструкция модели, а не гарантия качества свободного текста.

### Веб и синхронизация

Над списком — чипы сохранённых тем с точным общим числом связей и отдельной меткой `✨ AI`; AI-черновики обозначены пунктиром. Выбор чипа фильтрует таблицу. Поиск/категория/прочие фильтры сохраняются, поэтому число показанных строк может быть меньше общего числа связей в заголовке. Чипы без совпадений текущей выборки скрываются. Кнопка удаления с подтверждением доступна только Admin.

Внизу блока — последовательность «Выбрать группу похожих обращений» → «✨ Сгенерировать тему с ИИ» → «Сохранить тему в реестре». Первый шаг выбирает крупнейшую группу по категории/тегу; селектор позволяет перейти к другой группе. Без подбора AI анализирует текущую отфильтрованную выборку. Можно выбрать AI-черновик, сохранить или сбросить выбор; сохранение не запускается автоматически. Список ограничен по высоте и прокручивается внутри, панель завершает блок без перекрытия строк. Генерация ограничена 2–200 записями и 120 000 символами входа. Qvin по реестру убран из резерва на экране маршрутизации; аналитический диалог остаётся в реестре Admin/Manager.

Оба канала читают одну БД. Открытый веб подписывается на Supabase Realtime для тем и связей; дополнительно перечитывает их раз в 3 секунды и при возврате фокуса. Бот при каждом открытии списка читает актуальные данные. Уже отправленное сообщение Telegram является снимком: само по себе оно не обновляется после изменения в вебе. При разрыве соединения мгновенная доставка не гарантируется; после восстановления применяется резервное перечитывание. Удалённая тема снимает активный фильтр. Миграция добавляет обе таблицы в публикацию `supabase_realtime`.

### Telegram и синтетические данные

`/topics`, меню очереди/реестра и `/stats` дают кнопки «🔍 Подобрать похожие обращения», «✨ Сгенерировать тему (AI)», «Темы реестра». Подбор показывает группы с количеством. AI выдаёт заголовки и список реальных номеров/названий, затем «💾 Сохранить тему в реестре», «🔄 Перегенерировать», «❌ Отмена». ## Qvin в Telegram: совместимость и возврат (13.11.2026)

Подтверждён сбой `/qvin` → отдельный вопрос администратора: состояние уже `qvin`, но hosted `telegram_bridge(..., 'qvin')` возвращает `PT404 Request unavailable` до вызова модели. Приложение теперь при этом конкретном коде повторно проверяет роль admin/manager и читает последние 100 доступных записей через существующий `topics/rows`. Прямого service-role чтения всей таблицы нет; область ограничивает общий сервис тем. Этот совместимый путь не содержит impact-отчётов, поэтому денежный эффект и оценки трудозатрат из них недоступны. Нативный Qvin-маршрут продолжает передавать отчёты при их наличии.

На приглашении и ответе Qvin есть «К реестру» и «Завершить диалог»; завершение очищает состояние и открывает главную. «Ещё вопрос» сохраняет историю. При сбое AI сохраняется вопрос и доступен его повтор кнопкой. Ошибка доставки остаётся повторяемой в inbox, а не маскируется под ошибку AI. В подборе, генерации, сохранении, удалении и ошибках тем доступны возврат/главная.

Проверено: `tsc --noEmit`, `check-telegram.mjs`, `check-telegram-api.mjs`, `check-telegram-inbox.mjs`, `check-telegram-webhook.mjs`. Живой вызов Qvin на исходную разговорную фразу пользователя по авторизованной выборке из 63 записей вернул ответ со ссылками на ID; сообщения в Telegram диагностикой не отправлялись. Транспорт разделяет длинный ответ на сообщения с кнопками на последнем. Production deployment завершён со статусом READY; основной домен привязан к новой сборке. После выкладки `check-telegram-connection.mjs` подтвердил настроенный webhook, 0 ожидающих обновлений, готовность бота/Supabase, права приватного канала и доступность Qwen/Whisper. Диагностика не отправляла сообщения пользователям. Историческая ошибка доставки в getWebhookInfo относится к предыдущему дню; новой очереди на момент проверки нет.

Дополнительно PASS `check-telegram-delivery.mjs`: его устаревший mock дополнен пустыми таблицами feedback/feedback_votes, которые уже читает доставка. Сканер tracked-файлов продолжает находить две существовавшие до этой задачи инфраструктурные метки в старом отчёте и миграционном скрипте; новые изменения значений конфигурации не добавляют. База и привязки Telegram этой итерацией не изменялись.
