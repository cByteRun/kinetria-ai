# 04 — Технологии и запуск

Для MVP выбраны Supabase Auth, PostgreSQL и Data API. SQL-миграции версионируют схему и политики доступа, а `supabase-js` отправляет запросы с JWT текущего пользователя. Оба кабинета работают с одной карточкой и историей.

| Слой | Выбор | Назначение |
|---|---|---|
| Веб и API приложения | Next.js App Router и TypeScript | Экраны, серверная проверка входных данных и действия с обращениями |
| Аутентификация | Supabase Auth, `@supabase/ssr` и `@supabase/supabase-js` | Вход по email и паролю для заранее созданных тестовых аккаунтов. Права определяются профилем и ролью в БД |
| Хранение | Supabase PostgreSQL, Data API и Row Level Security (RLS) | Запросы через HTTPS с publishable key и JWT пользователя. RLS ограничивает доступ к строкам и при прямом обращении к API |
| Миграции | SQL в `supabase/migrations/`, Supabase CLI | Версионируем таблицы, индексы, роли доступа, политики RLS и функции для атомарных изменений |
| AI-черновик и сводка | Next.js вызывает локальную Ollama по HTTP или API OpenAI/Gemini с серверным ключом | Сервер проверяет поля и категорию черновика. Сводка использует поля карточки. На Vercel разрешён явно настроенный Groq |
| Вложения MVP | PostgreSQL `request_attachments`, скачивание через Next.js | До 3 × 1 МиБ, атомарно с регистрацией, чтение через RLS. Объектное хранилище — развитие |
| Проверка | Браузерные сценарии и проверки прямого Data API | Контроль переходов, повторной отправки, доступа к чужой карточке и публикации итога |

[Supabase Auth для SSR](https://supabase.com/docs/guides/auth/server-side) · [Data API](https://supabase.com/docs/guides/api) · [API-ключи](https://supabase.com/docs/guides/getting-started/api-keys) · [Приватные бакеты](https://supabase.com/docs/guides/storage/buckets/fundamentals)

## Стартер и структура приложения

Одно Next.js-приложение использует SSR-подход из официального `with-supabase`. В `lib/supabase/` находятся клиенты для браузера и сервера, `proxy.ts` обновляет сессию. Лендинг и кабинеты — страницы App Router, вход и запись обращений — Server Actions. Supabase хранит профили, категории, карточки и события. [Исходники шаблона](https://github.com/vercel/next.js/tree/canary/examples/with-supabase)

Интерфейс локализован через `next-intl` без языковых префиксов в URL. Светлая и тёмная темы задаются общими CSS-стилями и `app/workspace/adaptive.css`; переключатель находится в шапке кабинета. Выбор сохраняется в cookie при серверной отрисовке. Тексты кабинетов, входа и служебные подписи локализованы полностью. На мобильном основные разделы закреплены снизу; реестр отображается карточками.

Режим разработки без Supabase открывает предпросмотр интерфейса. Общий сценарий в двух сессиях использует подключённый проект Supabase.

## SQL-миграции и подготовка демо

1. При необходимости инициализировать конфигурацию CLI через `supabase init`. Миграции профилей, карточек, маршрутов и событий лежат в `supabase/migrations/`.
2. Привязать отдельный демопроект через `supabase link --project-ref <ref>`. Перед применением проверить `supabase --help` и `supabase db push --help` установленной версии CLI; явно выбрать нужный демопроект, затем применить миграции. Локальная проверка с `supabase start` и `supabase db reset` возможна при наличии Docker.
3. Подготовить тестовые аккаунты через `pnpm seed:demo`, затем последовательно выполнить `supabase/demo-data.sql`, `supabase/demo-routing.sql`, `supabase/demo-layout.sql` на демопроекте.
4. Для AI явно задать `AI_PROVIDER=groq|ollama|openai|gemini` и соответствующую модель/ключ (`OLLAMA_MODEL`, `OPENAI_API_KEY`, `GEMINI_API_KEY`; подробности в README). В запрос уходит только описание, выбранный язык и справочник категорий. Ручная подача доступна при отсутствии ключа.
5. Для приложения задать `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Ключ с повышенными правами используется отдельным серверным скриптом подготовки аккаунтов и закрытым Telegram-транспортом. Обычные запросы приложения выполняются с JWT текущего пользователя.
6. Запустить Next.js локально или разместить приложение с доступом к демопроекту Supabase. Проверить вход под каждой ролью, сохранение истории и прямые обращения к Data API. В README указать зависимости от Supabase и модели, способ настройки серверного ключа, ручной режим подачи и запись сценария.

Инструкция по запуску и проверке в двух сессиях находится в [README](../README.md). [Руководство Supabase по миграциям](https://supabase.com/docs/guides/deployment/database-migrations) · [OpenAI Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create)

## Проверки текущих изменений

`node scripts/check-insights.mjs` проверяет нормализацию, изоляцию категорий, пересечения тем без удвоения KPI, порядок по частоте/приоритету и пустые выборки. `npx tsc --noEmit --noUnusedLocals` проверяет типы. `scripts/check-dashboard.mjs` проверяет серверные действия и RLS на синтетических данных. `scripts/check-p0-browser.mjs` — сквозной путь с созданием тестовых обращений.

Для повторной проверки мобильных экранов используйте `scripts/check-mobile-browser.mjs` с установленным Playwright и работающим сервером. Он читает существующие тестовые записи, проверяет роли, темы, группы и ширины 320/390/768/1440; отчёт и скриншоты сохраняются в игнорируемом `docs/evidence/mobile-review/`. Настройка `PLAYWRIGHT_MODULE`, `PLAYWRIGHT_EXECUTABLE_PATH` и `P0_BASE_URL` аналогична P0.

`node --env-file=.env.local scripts/check-insights-access.mjs` сверяет KPI браузера с прямыми RLS-чтениями и переход к отфильтрованной группе. Он использует существующие тестовые аккаунты и те же параметры Playwright/сервера, без записи доменных данных.

### Локальный сервер и авторизация

`pnpm dev` явно использует порт 3000: повторный запуск завершится ошибкой занятого порта, вместо автоматического выбора другого порта. В репозитории нет запуска браузера через `--open`; при занятом порте используем уже запущенный сервер. Таймер `WorkspaceLive` обновляет данные раз в 30 секунд, а не запускает сервер; во время выхода он приостанавливается.

`AuthForm` использует native POST и 303, серверный Supabase-клиент поддерживает ограничение ожидания сети. Компоненты цикла и обе темы оформлены в `app/workspace/feedback.css` поверх существующих токенов. Проверки: `node scripts/check-auth-flow.mjs`, `node scripts/check-feedback-browser.mjs` с доступным Playwright/Chromium.

### Проверка локализации

`node scripts/check-i18n.mjs` проверяет одинаковые ключи RU/EN/KK, ICU, параметры, формы числа, месяцы и отсутствие русских UI-литералов в TSX. `node scripts/check-i18n-browser.mjs` с теми же переменными Playwright проверяет язык/тему от лендинга до выхода, четыре внутренние роли, разделы, карточки и 320 px. Доказательства — `docs/evidence/i18n/` (игнорируются Git). SQL-проверка `scripts/check-category-i18n.sql` выполняется через psql и откатывает изменения. До запуска редактора категорий применить миграцию `20261112095620_localized_categories.sql` к целевой базе; в этой задаче применена локально.

## Telegram и Groq

Серверный HTTP-транспорт без дополнительного bot-framework: `lib/telegram/{api,bot,delivery}.ts`. Groq Whisper `whisper-large-v3-turbo` распознаёт голос ≤120 секунд / 3 МиБ; текстовый Groq разрешён на Vercel только при явной конфигурации. Квоты free tier не гарантируют непрерывную доступность, предусмотрен ручной ввод. `SUPABASE_SECRET_KEY` используется исключительно серверным мостом с закрытой RPC, а не чтением рабочих веб-экранов.

Миграция `20261112105311_telegram.sql` применена к локальной тестовой базе. Не сбрасывать базу ради интеграции; миграция добавочная, существующие обращения сохраняются. Подготовка окружения, получение chat_id, webhook и планировщик — [TELEGRAM](TELEGRAM.md). Проверки: `node scripts/check-telegram.mjs` и откатываемый `scripts/check-telegram.sql`. Внешний E2E отмечается отдельно от локального SQL.

Для живого бота используется HTTPS webhook Next.js; локально — HTTPS-туннель. Polling отключён. Добавочная демомиграция — `20261112112646_telegram_demo_accounts.sql`. Включение gate/allowlist, команды `/demo` и ограничения — в [TELEGRAM](TELEGRAM.md). R-067 проверил реальную доставку; отдельные отчёты не подменяют полный человеческий сценарий.

## Telegram: инструкции ролей и webhook

После выбора аккаунта доступны инструкция текущей роли и кнопка дашборда → APP_URL/login; /help не меняет черновик. Сотрудник работает со своими обращениями, ответственный — с назначениями, руководитель — с направлением, администратор — с общим реестром и резервом; настройки остаются в вебе. Основной транспорт — HTTPS webhook Next.js на Vercel, polling отключён. Состояние, архивы демо и update_id уже хранятся в Supabase. Регистрация: pnpm telegram:webhook, проверка: pnpm telegram:check. [Запуск и ограничения](TELEGRAM.md).

В размещённом синтетическом контуре ранее проверены webhook, вход и реестр четырёх ролей; применены 11 миграций и подготовлены 9 демопрофилей и 20 обращений. Адреса и идентификаторы инфраструктуры задаются через окружение и не публикуются. Эта проверка не подтверждает redeploy последующих исправлений. [Результаты](VALIDATION.md#подключение-интеграционной-базы-и-живой-webhook).


## Ревью Telegram после 397c041

Локально проверен webhook → общий доменный Closed-Loop: создание/вложение → назначение и срок → уточнение/ответ → работа → решение/ознакомление, а также резерв администратора. Исправлены повторы после сбоев RPC и отправки, независимая доставка уведомлений, старые кнопки назначения и чтение полного вопроса/истории. Схема и права сохранены. Исправления ещё требуют redeploy; реальный Whisper и расписание outbox отдельно не подтверждены. [Находки, проверки и ограничения](CODE-REVIEW.md#ревью-миграции-telegram-polling--webhook).

## Асинхронный Telegram и трассируемость

Webhook сохраняет update в PostgreSQL до HTTP 200; `after()` и планировщик обрабатывают очередь с изоляцией пользователя, повтором и общим лимитером Telegram API. Требуются новая миграция, deployment и перерегистрация webhook; 50–100 RPS в целевой среде ещё не измерены.
