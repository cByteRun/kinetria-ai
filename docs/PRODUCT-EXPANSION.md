# Клиентский цикл, портал, потенциальный эффект и Qvin

Актуальность: 13.11.2026. Реализовано в коде; миграция проверена на локальной Supabase. Production-миграция и deployment этого расширения не выполнялись.

## Продуктово-архитектурный бриф

Источник: [ТЗ DOCX](TZ/ТЗ_на_разработку_системы_обратной_связи_и_предложений_сотрудников.docx), [Business Vision](BUSINESS_VISION.md), текущий код. ТЗ — проект документа для согласования. Датасет DOCX содержит синтетические примеры, а не измеренные потери.

Компания теряет сигналы о проблемах и улучшениях в разрозненных каналах. Внутренние обращения показывают затруднения процессов, клиентские отзывы — их внешние последствия. Их объединяет работа ответственного; доступ к исходным данным остаётся раздельным.

## Четвёртый сквозной сценарий

Клиент / сотрудник → приватный отзыв → внутренняя R-карточка с маршрутом категории → смысловые темы реестра → назначение/работа/решение ответственного → отдельный ответ автору → при необходимости публикация подготовленного текста → поддержка идеи и уведомление.

1. Веб: `/feedback`, вне закрытого каркаса дашборда, с общими предпочтениями языка/темы. Клиент после входа сразу попадает сюда. Сотрудники и обработчики переходят из навигации кабинета.
2. Telegram: `/feedback` / «💬 Портал фидбэков / Отзывы». Клиент и сотрудник вводят текст, выбирают тип и категорию, при желании указывают время, затем явно подтверждают черновик. Регистрация до подтверждения отсутствует. Поддержка идей доступна всем активным ролям.
3. Обработка: категория направляет связанную внутреннюю карточку руководителю либо в резерв. Действует существующая матрица назначений и переходов. Изменение внутреннего статуса обновляет внешний статус; implemented остаётся implemented, rejected/closed отображаются как closed. Внутреннее решение не копируется в ответ автоматически.
4. Ответ: обработчик в пределах своей зоны либо администратор пишет ответ и отдельные `public_title`/`public_description`. Без публикации их видят автор и обработчики. Публикация открывает подготовленный текст и ответ всем вошедшим участникам портала.
5. Уведомления: существующий durable outbox уведомляет автора, текущего ответственного и поддержавших опубликованную идею. Внешним участникам отправляются только безопасный статус и ссылка `fbopen`, ответственному — внутренняя карточка. Приватные уведомления работают и без настроенного общего канала. Расписание повторов использует существующий `/api/telegram/deliver`.

## Данные и права

Роль уже существовала: `client` в TypeScript и `public.kinetria_role`. Второй enum `CLIENT` не вводился.

Миграция: `supabase/migrations/20261113014456_client_feedback_impact_qvin.sql`.

- `requests.origin`: employee/client. Клиентский отзыв создаёт связанную R-карточку; клиенту по-прежнему запрещены прямое чтение requests, событий, файлов и внутренние RPC.
- `feedback`: приватный оригинал, автор, связь с R, одобренная копия, ответ, статус и версия. Оригинал не сериализуется постороннему читателю; внутренний ID не выдаётся клиенту в списке.
- `feedback_votes`: уникальность `(feedback_id,user_id)`; операции задают желаемое состояние поддержки и потому безопасны при повторной доставке.
- `request_enrichments`: результат JSON-обогащения. SELECT только обработчикам в пределах доступных R-карточек; запись только серверному service role. Клиент и сотрудник финансовые оценки не читают.
- RLS включён на всех новых таблицах. Сырые feedback/votes не имеют authenticated/anon grants. Узкий RPC `feedback_portal` проверяет активный профиль, авторство и зону обработки. SECURITY DEFINER находится в закрытой схеме с пустым search_path; публичная оболочка — invoker. Telegram bridge доступен только service_role и берёт личность из привязки.
- Повтор подачи использует ключ автора; изменённый повтор отвергается. Поддержка возможна только опубликованной идеи. Публикация проверяет версию. Лимит подачи — 20 отзывов от автора в час.
- Клиентский портал полупубличный: вход обязателен. Анонимная публикация, свободная регистрация и поисковая индексация не реализованы.

## Гибридная оценка эффекта

`lib/impact-estimator.ts`: `ImpactEstimatorService`, реализация `HybridImpactEstimator`, адаптер `ImpactFactsProvider`. Используется существующий провайдерный слой `lib/ai.ts`; зависимости и провайдеры проекта не заменялись.

Необязательный hint доступен в веб-форме обращения, в портале и Telegram. Внутренняя подача с hint и файлами проходит одной транзакцией `submit_with_impact`; портал тоже создаёт F/R-связь атомарно.

После новой подачи запускается необязательное обогащение. JSON содержит As-Is, To-Be, сэкономленные часы в месяц, область оценки, источник, допущения, качественный эффект, влияние Low/Medium/High/Critical, score 0–100, предложенные категорию и смысловую тему. Типы, диапазоны, обязательные поля и допустимые категории проверяются сервером. Предложения категории и приоритета не перезаписывают подтверждённые поля карточки.

Источники: `author` — автор явно сообщил экономию; `ai_scenario` — гипотеза с числовыми допущениями и областью; `unknown` — нельзя обоснованно оценить часы. Текущие затраты времени не равны будущей экономии. Нельзя придумывать проверенные бенчмарки или переводить выгорание в часы без основания. Допущения сохраняются и показываются рядом с оценкой.

Без адаптера денежные поля и ROI равны null. Адаптер может предоставить часовую ставку, валюту и стоимость внедрения. Потенциальная месячная стоимость времени = часы × ставка. Сценарный ROI за 12 месяцев = `(12 × месячная стоимость − стоимость внедрения) / стоимость внедрения × 100%`; при нулевой/неизвестной стоимости ROI не считается. Это стоимость потенциально высвобожденного времени, а не доказанное снижение ФОТ.

Сбой AI не отменяет зарегистрированную запись. В карточке обработчика есть повтор оценки. Существующие обращения не пересчитаны массово: оценку можно запросить из карточки. Без настроенного AI оценка явно недоступна.

## Два режима Qvin

- Structured Output: строгий JSON для обогащения; общая смысловая группировка использует существующий `semantic-topics` с проверкой ID и часовым кэшем по конкретной доступной выборке.
- Copilot: `lib/qvin.ts`, панель в реестре администратора/руководителя, Markdown через существующий безопасный `AiMarkdown`. Браузер передаёт только ID текущей отфильтрованной выборки. Сервер перечитывает тексты и оценки под RLS и отвергает несовпадение состава. Чужие данные из браузера не принимаются. При смене выборки диалог сбрасывается; история ограничена шестью парами.
- Telegram: `/qvin` или кнопка администратора/руководителя; последние 100 доступных карточек, включая origin и оценки. Это отдельная ограниченная выборка, а не фильтры открытого браузера. Следующие вопросы поддерживают диалог. Отправка — plain text без parse_mode.
- Веб-анализ ограничен 200 выбранными записями; витрина — последними 200 доступными, Telegram-меню показывает первые 30 из них. Ограничения явно показываются. Модель получает только разрешённые поля; инструкции в текстах трактуются как данные. Qvin не выполняет действий и должен ссылаться на ID, различать гипотезы и факты и не суммировать пересекающиеся оценки людей/отделов.

## Проверка и запуск

Применить миграцию к выбранному окружению стандартным процессом проекта, затем развернуть код. Сначала миграция: старый код остаётся совместим. Для обогащения нужны серверный `SUPABASE_SECRET_KEY` и настроенный AI. Ключ не передаётся браузеру. Telegram требует обычной настройки бота, привязки и планировщика. Реальные Б24/1С для этого этапа не нужны.

Подтверждено локально:

- Production build и строгий TypeScript. В sandbox Next не смог разобрать вывод дочернего TypeScript CLI; та же сборка вне sandbox прошла.
- `node scripts/check-impact-qvin.mjs`: валидация JSON/категорий/источника, неизвестные часы, отсутствие денег без ставок, адаптер, ROI и защита от нулевой стоимости, whitelist контекста.
- `node scripts/check-feedback-delivery.mjs`: безопасные уведомления автору/поддержавшим, внутренний callback ответственному, receipts, работа без общего канала; Telegram замокан.
- `node scripts/check-telegram.mjs` и `node scripts/check-semantic-topics.mjs`: регрессия бота, смысловых тем, кэша и прогресса.
- `docker exec -i supabase_db_modus_IDEA psql -Xq -v ON_ERROR_STOP=1 -U postgres -d postgres < scripts/sql/check-client-feedback.sql`: RLS, изоляция, оригинал/витрина, replay, голоса, версия, статус, запрет клиентских Telegram-подделок и outbox; ROLLBACK.
- `node scripts/check-telegram-webhook-workflow.mjs`: webhook → бот → настоящий локальный SQL для внутреннего и клиентского циклов; внешние AI/Telegram замоканы; ROLLBACK.
- `scripts/check-product-browser.mjs`: вход клиента → подача → модерация → публичная копия → поддержка; сохранение JSON-оценки и Qvin по фильтру → Markdown → сброс диалога. Локальная Supabase, мок AI; 18 сочетаний 320/768/1440 × RU/EN/KK × светлая/тёмная тема. Тест создаёт синтетические записи. Playwright задаётся через `PLAYWRIGHT_MODULE`/`PLAYWRIGHT_EXECUTABLE_PATH`, URL через `PRODUCT_TEST_BASE_URL`; запускать только в изолированной локальной среде.

Живые AI-ответы, внешняя доставка, production-миграция/deploy и измеренная экономия этим этапом не подтверждены. CSAT/NPS, независимая связь нескольких F с одной R, корпоративные адаптеры и доказательство причинности эффекта остаются развитием.

## Исправление совместимости со схемой (13.11.2026)

В подключённой базе проверено наличие 23 существующих обращений. Новый SELECT с `origin` получал 42703 на окружении без миграции и блокировал весь экран. `lib/registry-data.ts` повторяет запрос без нового поля только при ошибке отсутствующего `origin`; ошибки доступа и сети остаются видимыми. Новая схема сохраняет источник client/employee. Проверка: `node scripts/check-registry-schema-compat.mjs`.

Ошибка RPC портала теперь отображается вместе с интерфейсом портала, а не заменяет его целиком; недоступная запись заблокирована. Это совместимость при разном порядке обновления приложения/БД, а не применение миграции к удалённой базе. В ходе исправления удалённые данные и deployment не менялись.
