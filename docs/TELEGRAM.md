# 🤖 Telegram — настройка и сценарий №3

Бот задаётся переменной `TELEGRAM_BOT_USERNAME`; `your_bot` в примерах — placeholder. Код интеграции, SQL и логика диалога проверены локально. Ключи добавлены, приватный канал/права подтверждены; настоящее тестовое сообщение опубликовано и отредактировано (message_id=2). Groq text и Whisper HTTP проверены. Полный пользовательский голосовой сценарий ещё проходит приёмку. Для размещённого режима нужны HTTPS webhook и доступная серверу база. Секреты не отправлять в чат и не коммитить.

## Что такое webhook и chat_id

**Webhook** — URL нашего приложения: `https://<ваш-домен>/api/telegram/webhook`. Telegram отправляет на него сообщения и нажатия кнопок. Это не адрес, который нужно искать внутри Telegram.

**chat_id канала** — постоянный числовой ID получателя, обычно `-100…`. Создайте приватный канал, добавьте бота администратором с правами публикации и редактирования. Опубликуйте тестовый пост, скопируйте ссылку на него вида `https://t.me/c/1234567890/1` и выполните:

```sh
node scripts/telegram-channel.mjs 'https://t.me/c/1234567890/1'
```

Скрипт выведет `TELEGRAM_CHANNEL_ID=-1000000000000`. Здесь цифры — пример; используйте свою ссылку. Если ссылки нет и webhook ещё не установлен, после добавления бота/публикации поста можно прочитать доступные обновления:

```sh
node --env-file=.env.local scripts/telegram-channel.mjs
```

Существующий webhook скрипт не удаляет, обновления не подтверждает и не сбрасывает.

## Переменные и запуск

Имя бота, случайные `TELEGRAM_WEBHOOK_SECRET` и `CRON_SECRET` уже подготовлены в локальном `.env.local`. Значения секретов не выводились в чат. Токен BotFather, ключ Groq и ID канала уже добавлены пользователем и проверены без вывода секретов. Имя бота допускает ведущий `@`. Локальные настройки не переносятся на хостинг автоматически.

В `.env.local` и отдельно в окружении размещённого приложения:

```dotenv
TELEGRAM_BOT_TOKEN=<токен из BotFather>
TELEGRAM_BOT_USERNAME=VoiceChatGpt_Custom_bot
TELEGRAM_CHANNEL_ID=<ID приватного канала>
TELEGRAM_WEBHOOK_SECRET=<случайная строка из A-Z a-z 0-9 _ -, минимум 20 символов>
CRON_SECRET=<отдельный случайный секрет повторной доставки>
GROQ_API_KEY=<ключ Groq>
AI_PROVIDER=groq
GROQ_WHISPER_MODEL=whisper-large-v3-turbo
GROQ_TEXT_MODEL=qwen/qwen3.8-27b
APP_URL=https://<ваш-домен>
```

Также нужны существующие `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, серверный `SUPABASE_SECRET_KEY`. Он используется только серверным транспортом Telegram и подготовкой аккаунтов. В браузер этот ключ не передаётся. Рабочие веб-экраны продолжают читать данные с JWT/RLS пользователя.

1. Применить `supabase/migrations/20261112105311_telegram.sql` к нужной базе после существующих миграций. В этой задаче применена локально; hosted-база не изменялась.
2. Разместить приложение на HTTPS, задать окружение и пересобрать. Whisper работает на Groq, Vercel только передаёт ограниченный аудиофайл. Тяжёлая модель на Vercel не запускается.
3. Установить webhook (скрипт проверяет приватность канала и права бота):

```sh
node --env-file=.env.local scripts/setup-telegram.mjs https://<ваш-домен>
```

4. Настроить внешний планировщик GET или POST `/api/telegram/deliver` с заголовком `Authorization: Bearer <CRON_SECRET>`, например раз в минуту. Автосоздание cron на хостинге в эту задачу не входит. Неудачные задания получают backoff до часа, чтобы не блокировать всю очередь. Веб-действия и webhook также запускают доставку через `after()`, но при сбоях внешний повтор нужен обязательно.
5. Под каждой тестовой ролью войти на сайт → «Как работает маршрут» → Telegram → создать ссылку → открыть и нажать Start. Ссылка одноразовая, живёт 10 минут. Обычный вход не позволяет выбрать роль или привязать чужой аккаунт через username; закрытый деморежим описан ниже.

`setWebhook` указывает `max_connections=40`; БД дополнительно сериализует шаги одного пользователя. Повтор update_id не повторяет завершённые действия. Сбой до завершения допускает повтор после освобождения lease; регистрация дополнительно идемпотентна по ключу черновика.

## Диалог по ролям

| Роль | Доступные действия |
|---|---|
| Сотрудник | `/new`: текст/голос → черновик → категория, тип, тема, описание, предложение, теги, файлы → подтверждение. `/list`: свои обращения, уточнение/ответ, решение, ознакомление, комментарии и история |
| Руководитель | `/list`: категории своего направления. Открыть → выбрать ответственного → срок `YYYY-MM-DD` или `-` → подтвердить. Рассмотрение, шаг, уточнение и решение |
| Ответственный | Только текущие назначения; рассмотрение, вопрос, шаг, решение, комментарий и история. После переназначения прежняя карточка недоступна |
| Администратор | `/stats` — сводка последних 30 доступных записей, `/reserve` — последние 10 открытых без владельца, назначение руководителя из резерва, комментарии/история. Категории и маршруты на сайте |

`/cancel` отменяет текущий диалог, `/unlink` отключает привязку и удаляет черновик. `/list` возвращает последние 10 записей по created_at DESC, number DESC; в кнопках порядок обратный, самое новое внизу, полный реестр/поиск/аналитика остаются в вебе. Интерфейс бота MVP — русский; веб-интерфейс RU/EN/KK.

Голос: до 120 секунд и 3 МиБ; распознавание `whisper-large-v3-turbo`. Сбой/лимит Groq предлагает текстовый ввод. AI предлагает только черновик; исходная расшифровка остаётся описанием и редактируется сотрудником. Неясную категорию выбирают кнопкой. Свободный текст не превращается автоматически в подтверждённое решение. Вложения: до 3 × 1 МиБ, доступны только после проверки прав на карточку. Голосовой оригинал не сохраняется в реестре как вложение.

## Канал и адресные уведомления

Канал — внутренняя служебная лента, а не реестр с общим доступом. Сообщение содержит номер, название категории, нейтральную тему «внутреннее обращение сотрудника», статус назначения и срок. **Не публикуются** исходные тема/описание, автор, предложение, решение и материалы. Категория и имена руководителя/назначенного в событии назначения видны участникам канала; состав канала ограничивает администратор компании.

После назначения исходное сообщение обновляется; отдельное событие показывает инициатора и выбранного ответственного. Снимок назначения сохраняется в outbox, поэтому последующие изменения не переписывают смысл события. Полная карточка открывается в личном боте с повторной проверкой прав. Личные уведомления идут автору и текущему назначенному. Остальные ответственные не получают персональную рассылку. Канал при этом виден всем его участникам — это согласованная общая лента.

Триггер БД создаёт outbox и для веб-изменений, и для Telegram. Доставка не откатывает бизнес-действие. Обрабатываются до трёх заданий за вызов, сохраняется прогресс по получателям, есть lease и повтор. Доставка **at least once**: при сбое между Telegram API и записью подтверждения возможен дубль сообщения. Exactly-once и подтверждение прочтения Telegram не заявляются. Тексты решений доступны после открытия карточки; личное push-сообщение сообщает о статусе без содержимого решения.

Привязки, токены, черновики и очередь закрыты для anon/authenticated Data API. Bridge доступен только service_role; внутри роль берётся из активного профиля, права на чтение проверяются явно, изменения используют существующие доменные RPC и версии. Приватные черновики старше суток, истёкшие ссылки и завершённые update_id старше недели удаляются при доставке (нужен работающий планировщик). При отзыве роли/назначения доступ прекращается, уже отправленные Telegram-сообщения автоматически не удаляются.

## Сценарий №3 для живой приёмки

1. Привязать четыре разных Telegram-аккаунта к сотруднику, руководителю IT, выбранному и неназначенному ответственным; отдельно администратор при проверке резерва.
2. Сотрудник: `/new`, голосом «В каталоге SYN-001 и SYN001 — один товар, приходится сверять вручную. Предлагаю единый справочник». Проверить расшифровку, выбрать «Каталог и данные», поправить тему, добавить синтетический файл.
3. До подтверждения в реестре нет новой записи. Отправить → получить R-номер → найти тот же номер на сайте. Повтор webhook/старой кнопки не создаёт дубль.
4. Проверить служебную карточку в приватном канале без исходного текста/файла. Руководитель открывает `/list`, находит R-номер, выбирает ответственного и срок; до подтверждения они не меняются.
5. Подтвердить → проверить владельца, срок и историю в вебе, обновлённое сообщение и отдельное событие назначения в канале. Выбранный получает личное уведомление, неназначенный — нет; его прямое открытие карточки отклоняется.
6. Ответственный: принять на рассмотрение → запросить уточнение; сотрудник отвечает. Зафиксировать следующий шаг и относящееся к проблеме решение: «Согласован SYN-001; SYN001 сохранён как алиас». Все действия видны на сайте.
7. Автор получает личное уведомление, открывает решение, отмечает ознакомление. Проверить историю и результат после повторного открытия.
8. Дополнительно: администратор открывает `/reserve`, назначает руководителя карточке без маршрута; настройки категорий проверяет через Web Dashboard. Отключить Groq/повторить webhook/изменить версию и проверить ручной путь, отсутствие дубля и отказ устаревшего действия.

Живая приёмка отмечается только после фактического прохода с номерами обращений и подтверждением сообщений. Локальный SQL PASS не подтверждает сетевую доставку или качество распознавания речи.

## Webhook на Vercel и локальная разработка

Polling отключён. Next.js принимает обновления на `POST /api/telegram/webhook`, сохраняет update в inbox перед 200 и запускает обработку через `after()`; 503 возвращается при недоступности приёма в БД. `runtime=nodejs`, `maxDuration=60`. Уведомления обрабатывает durable outbox; внешний планировщик повторов остаётся обязательным для восстановления после сбоев.

`pnpm telegram:webhook` берёт HTTPS origin из APP_URL (или аргумента), проверяет защищённый probe и Supabase до setWebhook, затем сверяет getWebhookInfo. Ожидающие обновления не сбрасываются, max_connections=40. `pnpm telegram:check` проверяет тот же endpoint и очередь. Секрет задаётся одинаково локально и в Vercel. Production URL должен принимать запрос Telegram без Vercel Login.

Для локальной разработки: Supabase → `pnpm dev` → HTTPS-туннель к порту 3000 → APP_URL туннеля → `pnpm telegram:webhook`. Для Vercel используйте размещённую Supabase. Старый polling-скрипт намеренно завершается с ошибкой и инструкцией.

Состояние уже хранится в Supabase через service-only RPC: `telegram_sessions` обновляет JSON текущего шага/черновика по Telegram ID; `telegram_demo_sessions` сохраняет его при переключении аккаунтов; `telegram_updates` защищает от повторов и параллельной обработки. Сброс процесса Vercel не сбрасывает диалог. После суток неактивности черновик очищается при запуске доставки. Новая схема/миграция для webhook не нужна.

## Инструкция выбранной роли

После выбора любого демоаккаунта есть кнопка «Как пользоваться» с его ролью. `/help` и эта кнопка загружают инструкцию текущего профиля из context, не принимают роль из callback и не изменяют черновик. Сотруднику объясняются подтверждение, уточнение и ознакомление; ответственному — назначения и решение; руководителю — очередь направления и назначение; администратору — общий реестр, резерв и настройки в вебе. Права проверяются прежними RPC. Инструкция и сообщения о веб-аналитике содержат переход на APP_URL/login.

Production origin задаётся через APP_URL. Webhook ранее зарегистрирован с интеграционной Supabase; реальные адреса и ID хранятся в окружении. [Проверка подключения](VALIDATION.md#подключение-интеграционной-базы-и-живой-webhook).

Локально проверен webhook → общий доменный Closed-Loop: создание/вложение → назначение и срок → уточнение/ответ → работа → решение/ознакомление, а также резерв администратора. ## Telegram: главное меню и совместный показ (12.11.2026)

`/start` и `/home` открывают меню текущего аккаунта, `/help` объясняет общий Closed-Loop и действия его роли. Эти переходы сохраняют текущий шаг и черновик; `/draft` возвращает сохранённый черновик сотрудника. Кнопка «🏠 Главная» возвращает меню, включая меню администратора с общим реестром, сводкой и резервом. `/cancel` явно отменяет шаг. Для ещё не привязанного участника `/start` объясняет вход; участнику закрытого демо предлагает выбор аккаунта.

Демоаккаунт остаётся активным до выбора другого через `/login` или `/unlink`; сам вызов `/login` лишь открывает выбор. Веб и бот используют общие обращения и историю; для того же доступа на сайте нужно войти в тот же аккаунт. Переключение в боте не переключает веб-сессию.

Для 2–3 участников каждый использует отдельный аккаунт и свой Telegram. Например: сотрудник создаёт и подтверждает обращение, руководитель нужной категории назначает ответственного, ответственный фиксирует решение, сотрудник читает итог. Каждый привязывает свой аккаунт одноразовой ссылкой из веб-справки; в закрытом демо выбирает отдельный свободный профиль. Нужны включённый demo gate и allowlist всех участников. Уведомления приходят автору и текущему назначенному, а доступ руководителя определяется категорией.

Один веб-аккаунт допускает один Telegram (`telegram_links.user_id unique`). Повторная привязка через ссылку сайта заменяет старую привязку; закрытое демо вместо перехвата отклоняет занятый аккаунт. Одновременное редактирование одной карточки защищено её версией: после конфликта нужно открыть её заново. Эти ограничения уже есть в схеме, новых миграций не требуется.

Setup регистрирует `/start`, `/home`, `/help`, `/login`, `/new`, `/draft`, `/list`, `/stats`, `/reserve`, `/cancel`, `/unlink` и сверяет ответ `getMyCommands`. Команды ролей помечены в описаниях; видимость команды не даёт прав. Демовход доступен только разрешённым участникам. Новое меню на размещённом боте требует доставки текущего кода и повторного `pnpm telegram:webhook`; локальные проверки не подтверждают это действие.

## Асинхронная обработка и запуск новой версии

После миграции `20261112181447_telegram_async_inbox.sql` webhook сохраняет update до ACK и запускает inbox в `after()`. Защищённый `/api/telegram/deliver` теперь дренирует inbox и outbox; внешний планировщик с CRON_SECRET нужен для восстановления без трафика (рекомендуется раз в минуту). Перерегистрировать webhook через `pnpm telegram:webhook`: max_connections теперь 40. До применения миграции новую версию не размещать. [Полный runbook, гарантии и ограничения нагрузки](10-e2e-flows-and-traceability.md#запуск-и-проверка).


Текущая итерация: структурированная инструкция, эмодзи/группы кнопок, возвраты без изменения черновика, явный `attach` и имена вложений. Setup регистрирует `default` + `all_private_chats`, очищает русские переопределения и включает меню commands; требуется повторный `pnpm telegram:webhook`.
