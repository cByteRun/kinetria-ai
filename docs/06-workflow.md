# 06 — Рабочий процесс команды

Начинаем с единого сценария по мотивам A-003. Дизайн, доменная логика и демоданные используют одни статусы и роли из [доменных правил](03-domain.md). Каждую функцию доводим до экрана и проверяем на тестовых ролях.

| Зона | Результат |
|---|---|
| Продукт и дизайн | Чат с предпросмотром, CRM-доска, тексты ошибок и карточка с итогом |
| Разработка | Миграции, API, доступ, журнал событий и рабочие экраны |
| Данные и проверка | Воспроизводимая загрузка синтетического набора, проверки переходов и контрольные сценарии |
| Защита | Прототип, материалы подачи, демодоступ, резервная запись и репетиция по таймеру |

Один участник может вести несколько зон. При изменении статуса, поля или права обновляем правила, пример данных и экран в одной задаче. Для каждой задачи фиксируем экран или действие, ожидаемый результат и способ проверки. Перед сборкой показываем изменение под реальной тестовой ролью и проверяем недоступность для чужой роли.

## Проверка перед демонстрацией

- Чистый запуск, миграции и импорт демоданных выполняются по инструкции.
- До подтверждения AI-черновика в CRM нет записи. Повтор отправки создаёт одну запись. Ошибка изменения оставляет прежний статус.
- Запись без владельца видна в очереди, просрочка фильтруется, назначение отражается в истории.
- Автор открывает уведомление, читает итог в карточке и отдельно подтверждает ознакомление.
- Другой автор не может открыть запись, события или файл. Руководитель видит только свои очереди.
- Сводка совпадает с контрольными числами до интерактивных изменений.
- Репетиция, ссылки и описание реализации соответствуют фактической сборке.

## Синхронизация и ревью

При изменении реализации сверяем историю коммитов и обновляем документы 00–07, спецификацию экранов и README в одной задаче. Business Vision задаёт продуктовую цель; планы и работающие функции обозначаем отдельно. Официальные даты и непроверенные внешние факты без новых источников не изменяем.

Перед показом дополнительно проверяем ширины 320, 390, 768 и 1440 px, обе темы и сохранение выбора, читаемые подписи мобильной навигации, карточку реестра и раскрытие темы. Сотрудник/клиент не должны открывать аналитику прямой ссылкой. Для ответственного, руководителя и администратора числа вычисляются только по их доступным карточкам. Несколько тегов не удваивают общие KPI.

Коммит оформляем Conventional Commits от настроенного автора Git. Результат ревью и точные ограничения проверки: [CODE-REVIEW](CODE-REVIEW.md).

### Дополнительная приёмка входа и обратной связи

Проверяем вход → кабинет без ручного обновления → выход → прямой защищённый URL → вход. Проверяем неправильный пароль, состояние ожидания, обычную отправку без JavaScript и запрет чужого Origin. Не запускаем второй dev-сервер ради проверки.

Для карточки проверяем читаемость владельца, срока, решения и истории; на мобильном — закрепление панели при прокрутке и доступность последней кнопки над ней. В обеих темах проверяем обычное и hover-состояние результатов. В уведомлениях проверяем фильтры и различие между прочтением обновления и ознакомлением с решением.

### Приёмка локализации

Перед merge обязательны `node scripts/check-i18n.mjs` и `npx tsc --noEmit --noUnusedLocals`. Новая UI-строка добавляется одновременно в RU/EN/KK; переменные и множественные формы оформляются ICU. Коды БД не переводятся. Браузерный прогон проверяет смену языка без потери черновика, сохранение cookie после перезагрузки/выхода, все роли и отсутствие hydration/MISSING_MESSAGE ошибок. Не сохраняем уже переведённые подсказки в состоянии: храним ключ, переводим при рендере.
