## Оставшиеся ограничения ревью

1. **P2 — размер выборки.** `components/request-workspace.tsx` получает карточки одним запросом без пагинации, счётчики оболочки делают аналогичный запрос. Если доступных строк больше серверного лимита Data API, реестр и агрегаты окажутся неполными. Текущая проверенная демобаза меньше лимита. Перед пилотом с большим объёмом нужны пагинация и агрегаты с RLS на сервере, а не увеличение клиентского набора без ограничений.
2. **P2 — время содержательного ответа.** `supabase/migrations/20261112005114_live_dashboard.sql:31` устанавливает `first_response_at` при выходе из `new`. Подпись «До рассмотрения» соответствует текущему поведению. Для KPI ответа автору потребуется отдельное событие/поле и пересмотр истории; исторические данные не переписывались.
3. **Продуктовая граница.** Общая категория и тег не подтверждают дубликат, причину или уникальное внедрение. Нет таблицы подтверждённых связей и счётчика уникальных авторов. Интерфейс не обещает автоматического слияния; исходные карточки, статусы и решения остаются отдельными.
4. **Локализация.** Новые подписи кабинетов преимущественно русские; полноценная EN/KK-локализация этих подписей ещё не выполнена.

## Готовность Telegram к QR-показу на 50–100 участников (12.11.2026)

Метод: статическое ревью текущего кода. По уточнению пользователя нагрузочный запуск не выполнялся. Нет измерений RPS, p95, ошибок, облачных лимитов или времени ожидания; локальные регрессионные проверки не являются нагрузочными.

### Находки по приоритету

1. **P1 · Массовый вход блокируется моделью демо.** `lib/telegram/demo.ts:5–11`, `lib/demo-accounts.json`, `20261112105311_telegram.sql:4`, `20261112112646_telegram_demo_accounts.sql`: восемь общих внутренних профилей, allowlist Telegram ID и уникальный профиль в привязках. Даже при включённом gate 50–100 зрителей не смогут одновременно выбрать эти роли. Не разрешённый ID не получает демовход. Обычная привязка того же веб-аккаунта заменяет предыдущий Telegram. До публичного QR нужны отдельные синтетические идентичности участников с ограниченной областью и временным доступом либо отдельный массовый сценарий предпросмотра. Снимать unique или открывать всем общие привилегированные профили недостаточно: это разрушит изоляцию.
2. **P1 · Медленный участник задерживает общую входящую очередь.** `scripts/setup-telegram.mjs:41`, `app/api/telegram/webhook/route.ts:18`, `lib/telegram/api.ts:103–111`: `max_connections=1`, HTTP-ответ только после обработки, голос/AI и отправка Telegram выполняются внутри неё. Суммарное ожидание burst зависит от суммы времени предыдущих обновлений. Иллюстрация, не замер: если обновление занимает 1 секунду, очередь из 100 обновлений требует около 100 секунд без учёта повторов. Просто увеличить connections без проверки порядка сообщений и retry нельзя; нужны ограниченный параллелизм между пользователями и сохранение последовательности внутри диалога.
3. **P2 · Нет обработки интервала Telegram при ограничении отправки.** `lib/telegram/api.ts:59`, `lib/telegram/delivery.ts:80`: ответ API превращается в общую ошибку без чтения `parameters.retry_after`. Прямой ответ бота вызывает retry webhook; outbox использует собственный backoff. Для массовой подачи и общего канала нужна общая регулировка отправки с учётом ответа API; иначе задержки и повторы увеличатся. Точный порог срабатывания здесь не устанавливался.
4. **P2 · Повторная доставка не имеет подтверждённого постоянного запуска.** `app/api/telegram/webhook/route.ts:19`, `lib/telegram/delivery.ts:18,80`: после успешного webhook берутся максимум три outbox-задания; ошибка откладывает задачу. После окончания активности повтор потребует нового вызова worker. Endpoint планировщика есть, но его размещённое расписание не подтверждено. Перед показом проверить постоянный drain и остаток очереди после сбоев; иначе зарегистрированное обращение может остаться без своевременного уведомления.

### Что уже помогает

Права проверяются по текущему профилю, выдача бота ограничена 10/30 записями, история постраничная. Есть ключ регистрации без дублей, проверка версии карточки, durable outbox, lease и сериализация обновлений одного Telegram ID. Эти механизмы снижают риск потери/смешивания данных, но не доказывают ёмкость БД или всего сервиса.

### Решение для показа

Текущий закрытый Telegram-демовход подходит ограниченному числу заранее подключённых участников, а не одновременному входу зала по QR. Массовый QR-вход пока не готов. Веб и Telegram следует проверять отдельно: ограничения Telegram-привязок не доказывают ограничение числа веб-сессий. Для следующей приёмки нужны 50/100 независимых идентичностей, смесь действий сотрудника/руководителя/ответственного/администратора, проверка очереди, конфликтов, изоляции и повторной доставки, затем отдельная проверка внешних Telegram/Groq. Изменения инфраструктуры и модели демодоступа этим ревью не выполнялись.

### Следующие улучшения

1. Реестр и счётчики всё ещё читают набор карточек, а shell частично дублирует чтения страницы. Для большого объёма нужны серверная пагинация, RLS-агрегаты и согласованная серверная фильтрация; иначе лимит Data API ограничивает полноту данных. Общий force-cache персональных выборок не добавлялся. `getProfile` уже использует React.cache в пределах запроса.
2. Счётчики shell всё ещё ждут БД; следующая архитектурная оптимизация — отдельная потоковая граница для счётчиков или агрегированный RPC. Добавленные loading/Suspense обеспечивают обратную связь, но не устраняют сетевую задержку Auth/БД.
3. Общий ui остаётся крупнейшим клиентским пространством. Его дальнейшее деление требует согласовать namespaces потребителей и границы providers по экранам. Смена языка закономерно запрашивает серверные переводы; сохранение состояния проверено, мгновенность без сети не заявляется.
4. Тяжёлых внешних библиотек графиков нет: графика реализована SVG/CSS. ssr:false для видимых секций и искусственное дробление маленьких модулей не вводились; дальнейший dynamic import оправдан после анализа реального route bundle либо добавления тяжёлого редактора.
5. Оптимистичные изменения статуса/решения требуют согласовать отображение конфликтов версий и возврат при отказе RPC. Для доменных действий сохранены существующие проверки и revalidatePath, оптимистична только безопасная настройка темы.
6. Следующий замер — route timings, LCP/INP/CLS и JS transfer на целевом deployment/мобильной сети с одинаковыми данными до/после. Локальный build и Chromium не доказывают эти показатели. Визуальная геометрия проверена, измеренный нулевой CLS не заявляется.
