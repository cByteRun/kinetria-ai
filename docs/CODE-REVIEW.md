## Оставшиеся ограничения ревью

1. **P2 — размер выборки.** `components/request-workspace.tsx` получает карточки одним запросом без пагинации, счётчики оболочки делают аналогичный запрос. Если доступных строк больше серверного лимита Data API, реестр и агрегаты окажутся неполными. Текущая проверенная демобаза меньше лимита. Перед пилотом с большим объёмом нужны пагинация и агрегаты с RLS на сервере, а не увеличение клиентского набора без ограничений.
2. **P2 — время содержательного ответа.** `supabase/migrations/20261112005114_live_dashboard.sql:31` устанавливает `first_response_at` при выходе из `new`. Подпись «До рассмотрения» соответствует текущему поведению. Для KPI ответа автору потребуется отдельное событие/поле и пересмотр истории; исторические данные не переписывались.
3. **Продуктовая граница.** Общая категория и тег не подтверждают дубликат, причину или уникальное внедрение. Нет таблицы подтверждённых связей и счётчика уникальных авторов. Интерфейс не обещает автоматического слияния; исходные карточки, статусы и решения остаются отдельными.
4. **Локализация.** Новые подписи кабинетов преимущественно русские; полноценная EN/KK-локализация этих подписей ещё не выполнена.

Polling был последовательным процессом с постоянным циклом outbox; webhook зависит от сохранённых сессий/update_id, повторов HTTP и отдельного планировщика доставки.

### Сверка ролей и P0

- Сотрудник: текст/голос → редактируемый черновик → активная категория/вложение → явное подтверждение → общая запись; затем ответ на уточнение и ознакомление с итогом.
- Руководитель: только категории направления, назначение допустимого участника и срока; рассмотрение → вопрос → ответ автора с возвратом на рассмотрение → следующий шаг → содержательное решение.
- Ответственный: только текущие назначения; те же разрешённые переходы. Переназначение отзывает прежний доступ.
- Администратор: общий реестр, история/комментарии и резерв → назначение руководителя. Публикации решения нет; категории/маршруты и полная аналитика остаются в вебе согласно Business Vision.
- Закрытие требует решения; уведомление и отдельное ознакомление не подменяют результат внедрения. SQL-схема, переходы и права не расширялись; новая миграция не нужна.

### Проверки и границы доказательства

`node scripts/check-telegram-webhook-workflow.mjs` — **PASS**. Реальный обработчик HTTP → реальный бот → реальный API adapter → PostgreSQL-функции локального Supabase. Всё выполняется в одной транзакции с ROLLBACK; тест не отправляет сообщения людям. Голос заменён готовой расшифровкой, Telegram API и AI заглушены. Проверены файл/подтверждение, автоматическое назначение, ручное назначение и срок, полный вопрос после 9 комментариев, страницы истории, ответ, работа, результат и ознакомление; резерв администратора, запрет чужому ответственному, конфликт версии/старого подтверждения, временный сбой БД с 503 и повтор submit после сбоя отправки без дубля и с восстановлением R-номера. Прямой SQL-тест дополнительно проверяет grants, одноразовую привязку, запрет пустого решения и отзыв прежнего назначения.

Для запуска нужны существующий локальный контейнер `supabase_db_modus_IDEA` (можно задать `TELEGRAM_TEST_DB`), актуальные миграции и синтетические профили четырёх ролей. Auth-провайдер не вызывается; тестовые привязки создаются внутри откатываемой транзакции. Автономные sequence-счётчики PostgreSQL могут получить пропуски после ROLLBACK.
