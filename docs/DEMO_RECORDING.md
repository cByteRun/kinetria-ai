# Воспроизводимые E2E GIF · 13.11.2026

Записи создаются Playwright из текущего интерфейса IdeaRoute. Источник — локальный браузер и работающая локальная Supabase, не смонтированные макеты экранов. Данные синтетические. [GIF и технический manifest](demos/manifest.json).

Telegram-стенд **не является web.telegram.org**. Он рендерит настоящие тексты и callback-кнопки обработчика и передаёт нажатия в настоящий webhook. Для доставки используется настоящий `delivery.ts` с SQL-адаптером Data API; граница Telegram API заменена сбором сообщений в браузере. Служебная карточка в канале обновляется, личное уведомление возвращается автору. Изменение статуса происходит в личном боте. SQL-транзакция Telegram откатывается по Ctrl+C; веб-сценарии оставляют явно синтетические записи в локальной БД.

## Подготовка

1. Выполнить локальный quick start из [README](../README.md#setup): Docker, Supabase, все миграции, аккаунты, четыре SQL seed. Настроить `.env.local` с демопаролем. Использовать исключительно изолированную локальную БД.
2. Установить Playwright/Chromium отдельно от runtime приложения, например `npm install --prefix /tmp/idearoute-recording playwright`, затем `node /tmp/idearoute-recording/node_modules/playwright/cli.js install chromium`; доступны overrides `PLAYWRIGHT_MODULE` (путь к `index.mjs`) и `PLAYWRIGHT_EXECUTABLE_PATH`.
3. Для кодирования установить Pillow и imageio-ffmpeg в отдельное Python-окружение. Зависимости записи не меняют приложение и lockfile.
4. Запустить `node scripts/start-demo-recording.cjs`. Скрипт читает **локальный** `supabase status -o json`, проверяет localhost и подставляет локальные API-ключи, не выводя их. При необходимости задать `SUPABASE_CLI` (полный путь). Next.js — порт 3016, build-dir `.next-demo`; настоящий токен Telegram отключён, AI — маркированный адаптер.

## Запись — строго последовательно

В отдельном терминале:

```sh
node scripts/record-demos.mjs
```

Веб-recorder проверяет ответы, сохранение и результат действий; поддерживает `DEMO_BASE_URL` (только localhost) и `DEMO_ONLY=1|2|3|5`. Сценарий 2 заранее создаёт отдельную синтетическую карточку через веб и затем проводит её один UUID через роли. Повтор прогона создаёт новые синтетические карточки.

**После завершения веб-записи**, запустить в другом терминале:

```sh
DEMO_TELEGRAM_SERVER=true node scripts/check-telegram-webhook-workflow.mjs
```

Он открывает `http://127.0.0.1:3018`, использует существующий локальный контейнер `supabase_db_modus_IDEA` (override `TELEGRAM_TEST_DB`). Его открытая SQL-транзакция может блокировать веб-изменения — параллельно веб-recorder не запускать. Записать:

```sh
node scripts/record-telegram-demo.mjs
```

Остановить Telegram-стенд Ctrl+C: выполняется ROLLBACK. Затем кодировать:

```sh
python3 scripts/encode-demo-gifs.py
```

При нестандартном Python-окружении задать `PYTHONPATH`, при готовом ffmpeg — `--ffmpeg /path/to/ffmpeg`. Записи сохраняются в игнорируемый `docs/evidence/demo-recording/`; окончательные GIF и `manifest.json` — в `docs/demos/`. Encoder: 25 fps из исходных Playwright WebM (40 мс на кадр), веб 1280 px / Telegram 1152 px, единая палитра 256 цветов на всю запись. Палитра строится отдельным проходом по всему ролику; упорядоченный Bayer dithering сохраняет неподвижный рисунок градиентов, без случайного шума и смены палитры по кадрам. `mpdecimate` убран: промежуточные кадры движения сохраняются. Последний кадр удерживается 2 секунды; скорость действий и паузы исходника сохранены. 30/60 fps не заявляются: источник содержит 25 fps. Manifest фиксирует размер, длительность, кадры, параметры кодирования, SHA-256 исходника и GIF. Перед заменой файла полностью декодируются кадры, проверяются размеры, цикл и задержки. `--only demo-1-submission-and-qvin` позволяет перекодировать один сценарий; `--force` — повторить весь выбранный набор.

## Дополнительный GIF: администратор меняет маршрутизацию

`node scripts/record-admin-routing-demo.mjs` записывает `demo-6-admin-routing.gif` на том же изолированном localhost. Администратор сохраняет два разных правила для категории, сотрудник регистрирует по одной карточке после каждого изменения; проверяются реальные владельцы в `dd` карточек. Изменение правила не меняет владельца старой карточки. В конце и при ошибке восстанавливается исходный маршрут. Маршрутизация не использует AI; фоновая оценка карточки в локальном стенде использует общий детерминированный AI-адаптер. GIF дополняет шесть основных сценариев README, а не вводит отдельное ограничение на число функций.

Production отдельно проверен `check-production-registration.mjs`: одна явно синтетическая карточка, реальный submit с файлом, скачивание и содержимое файла, reload, чтение администратором, доступность портала/тем. Тест требует явного `CONFIRM_PRODUCTION_SMOKE=true` и адреса `PRODUCTION_CHECK_URL`; создаёт запись в выбранном размещённом демо. [Отчёт исправления](PRODUCTION-REPAIR.md).

Новая запись маршрутов: [demo-6-admin-routing.gif](demos/demo-6-admin-routing.gif) — 7.16 МиБ, 54.77 с, 72 кадров. Декодированы все кадры шести GIF, проверены loop, SHA-256 и шесть ссылок README.
