## Общая техническая цепочка

`Telegram → POST webhook → secret + runtime validation → telegram_enqueue → 200 OK → after() → drainInbox → handleUpdate → bridge/RPC → общие requests/events/outbox → Telegram + веб`.

До `200 OK` выполняется только проверка входа и одна операция сохранения в PostgreSQL. При недоступной БД возвращается `503`, чтобы Telegram повторил доставку. Отправлять ACK до сохранения нельзя: завершение процесса иначе потеряет обращение. `after()` запускает обработку после ответа и ограничен временем функции; сам по себе он не является сохраняемой очередью. [Next.js after](https://nextjs.org/docs/app/api-reference/functions/after).

`telegram_inbox` сохраняет payload по уникальному update ID. `telegram_inbox_claim` выбирает до 10 голов очередей разных пользователей с `FOR UPDATE SKIP LOCKED`, advisory lock и lease на две минуты. Следующий известный update пользователя не обгоняет незавершённый предыдущий, включая отложенный повтор. Разные чаты работают параллельно. Порядок определяется `update_id` среди уже принятых записей: система не ожидает неизвестные ещё сетевые сообщения. UUID-token ограждает подтверждение задания от устаревшего обработчика. Существующие `telegram_updates` дополнительно защищают выполнение бота; `telegram_sessions` и демосессии хранят диалог в БД. `AsyncLocalStorage` содержит только цель редактирования текущего update и изолирует асинхронные запросы.

Один запуск делает до 10 батчей, не начинает новый после 20 секунд; уже начатые операции ограничены временем route (60 секунд). Двухминутная lease длиннее этого лимита. Повтор после ошибки: 2, 4, 8…256 секунд. После аварии без receipt — повтор после истечения lease. Защищённый `GET/POST /api/telegram/deliver` обрабатывает inbox и outbox независимо через `Promise.all`. Планировщик обязателен для восстановления без нового входящего трафика; рекомендуется вызов каждую минуту с `Authorization: Bearer <CRON_SECRET>`. Простой callback без сохраняемой записи здесь не используется.

## Сотрудник — обращение до результата

**Цель:** доступный канал и отсутствие потерянных инициатив (Vision §3–4; ТЗ §2.3, §2.5).

| Действие | Webhook / API / БД | Ожидаемый результат |
|---|---|---|
| Привязать аккаунт из веб-справки | Одноразовый токен → bridge `link` → активный `profiles` / `telegram_links` | Работа от собственного профиля; один Telegram на аккаунт |
| `/new`, отправить текст/голос | Сохраняемый update → `transcribe`/Groq → AI или ручной fallback → session state | Приватный черновик, запись в реестре ещё отсутствует |
| Проверить тип/категорию/текст, исправить или перезаписать | `showDraft`, `state`, `category`, `kind`, `rewrite`; последовательная очередь пользователя | Исходные факты проверены автором; неудачная перезапись сохраняет прежний черновик |
| Подтвердить отправку | `submit` → общий доменный `submit_with_files` с UUID-ключом | Одна R-карточка с автором, маршрутом/резервом, сроком и историей |
| Ответить на уточнение, прочитать итог | `reply/review`, затем `ack`, проверка версии и авторства | Содержательный ответ сохраняется, ознакомление фиксируется отдельно от доставки |

Успех: повтор webhook не создаёт вторую карточку; тот же R-номер доступен в вебе и боте. Регистрация требует явного подтверждения, AI не принимает решение за человека.

## Руководитель — рассмотрение и назначение

**Цель:** видимый владелец и ответственность за следующий шаг (Vision §4; ТЗ §2.2–2.5).

| Действие | Webhook / API / БД | Ожидаемый результат |
|---|---|---|
| Открыть `/list` или рабочий реестр веба | Bridge проверяет категории руководителя; веб читает через RLS | Только обращения направления; канал сообщает служебный статус без полного текста |
| Открыть карточку и принять на рассмотрение | `detail`, `review`, версия `requests` и событие истории | Автор видит начало рассмотрения |
| Выбрать допустимого ответственного и срок, подтвердить | `assignees` → шаги диалога → `assign`, общая SQL-транзакция | Назначение и срок согласованы; ошибка версии/даты откатывает действие |
| Запросить уточнение или опубликовать решение в своей области | Права и обязательный текст в доменных функциях | История и ответ доступны автору; решения не публикуются от имени AI |

Личное push-уведомление получают автор и текущий назначенный. Каждый руководитель направления не получает отдельную массовую рассылку: доступная очередь и канал обеспечивают обзор.

| Действие | Webhook / API / БД | Ожидаемый результат |
|---|---|---|

## Администратор — резерв, настройки и аналитика

**Цель:** обращения не теряются при отсутствии маршрута; решения дают материал для анализа (Vision §4–5; ТЗ §2.5–2.7).

| Действие | Webhook / API / БД | Ожидаемый результат |
|---|---|---|
| Открыть `/reserve`, назначить владельца | Общая карточка без назначения, `assignees/assign`, серверные права | Обращение выходит из резерва, исходный автор/история сохраняются |
| Перейти в дашборд | Кнопка → `APP_URL/login` → отдельная веб-сессия | Авторизация веба обязательна, роль бота не переносит cookie |
| Изменить категории и маршруты | Веб Server Actions/RPC с проверкой admin | Работают новые правила подачи; настройки не редактируются через бот |
| Открыть `analytics/insights` | Общие `requests/events`, фильтры периода и `lib/insights.ts` | Видны сроки, решения, реализованные карточки и темы; `/stats` ограничен 30 записями и не заменяет дашборд |

Среднее «первого ответа» сейчас означает начало рассмотрения. Число `implemented` считает карточки; общие KPI тем дедуплицируют ID. Ни наличие аналитики, ни очередь webhook не доказывают снижение затрат без пилотных замеров.

## Исходящие лимиты и гарантии

Все отправки из TypeScript-пайплайна, включая multipart `sendDocument`, проходят `telegram()` и общий SQL-лимитер. Интервалы допуска: глобально 40 мс (25 вызовов/с), приватный чат 1100 мс, канал/группа 3100 мс. Это консервативные интервалы относительно рекомендаций Telegram: около 30 сообщений/с для рассылки, около одного сообщения/с в чат и 20/мин в группу. Редактирования также включены в ограничитель. [Telegram FAQ](https://core.telegram.org/bots/faq#how-do-i-avoid-hitting-limits).

Слот выдаётся атомарно всем инстансам; ожидание асинхронное и ограничено 8 секундами. При `429` `parameters.retry_after` сохраняется как общий cooldown в БД, ошибка передаётся в сохраняемый повтор. Повтор может произойти позже указанного срока из-за backoff/расписания, но не отправляет раньше сохранённого cooldown. Сам API всё равно может вернуть `429`; его лимиты нельзя гарантировать локальным таймером. Сетевые задержки могут сместить фактическое время доставки относительно допуска.

`update_id` исключает повтор завершённого задания, lease исключает одновременное выполнение, UUID подачи исключает вторую регистрацию. Однако межсервисной транзакции между Telegram и PostgreSQL нет. После успешной отправки и потери ответа/receipt сообщение может повториться; некоторые изменения состояния перед сбоем также требуют повторного чтения. Поэтому гарантия — at-least-once обработка с доменной идемпотентностью, а не exactly-once всех внешних эффектов.

## Ревью и ограничения нагрузки

Подробные находки — [CODE-REVIEW](CODE-REVIEW.md#асинхронный-webhook-и-конкурентность-12112026). Исправлены ожидание бизнес-логики до ACK, глобальная сериализация webhook, отсутствие общего rate limiter и непроверенная структура входа. Существующие SQL/RBAC и изоляция состояния сохранены.

50–100 одновременных пользователей и 50–100 входящих RPS — разные режимы. Вход может накапливаться быстрее исходящих ответов: при устойчивых 100 update/с и хотя бы одном сообщении на update очередь растёт минимум на 75 ответов/с при выбранных 25/с. AI и Groq имеют отдельные квоты. Это нельзя устранить увеличением `max_connections`.

Открытые эксплуатационные вопросы: предел очереди и backpressure при длительной перегрузке; dead-letter/ручное восстановление постоянно ошибочного update (сейчас он блокирует только свой чат и повторяется); мониторинг backlog/возраста, попыток и ошибок; отдельная пагинация/агрегаты веб-аналитики. `telegram_inbox` оставляет компактную запись после успеха и очищает payload; удаление старых tombstone/ключей лимитера следует включить в согласованную политику хранения. Нельзя удалять ожидающие задания как обычный TTL-кеш.

## Запуск и проверка

1. Применить добавочную миграцию `20261112181447_telegram_async_inbox.sql` к целевой базе перед новым кодом. Она не меняет доменные карточки. Проверить закрытые права service_role.
2. Разместить Next.js с поддержкой `after()`/`waitUntil` и временем функции 60 секунд. Настроить прежние Telegram/Supabase/Groq переменные и `CRON_SECRET`.
3. Запустить `pnpm telegram:webhook`: теперь `max_connections=40`, readback проверяет это значение, pending updates не удаляются. Старый `max_connections=1` необходимо перерегистрировать.
4. Настроить внешний планировщик `GET/POST /api/telegram/deliver` с Bearer `CRON_SECRET`, рекомендуемый период — одна минута. После деплоя проверить восстановление сохранённого задания без нового webhook.
5. Выполнить живой синтетический голосовой проход четырёх ролей и отдельный нагрузочный тест целевой среды. Измерять ACK p50/p95/p99, долю 5xx, backlog/возраст, скорость дренирования и 429; очередь после всплеска должна опустеть. Целевой ACK p95 <500 мс — критерий будущей приёмки, не полученный здесь результат.

Локальные проверки: TypeScript; `check-telegram.mjs`, `check-telegram-api.mjs`, `check-telegram-webhook.mjs`, `check-telegram-inbox.mjs`, `check-telegram-webhook-workflow.mjs`; SQL `check-telegram-inbox.sql`; `check-telegram-inbox-concurrency.mjs`. SQL-проверки используют локальный Docker PostgreSQL: первая и workflow выполняют ROLLBACK, конкурентная создаёт и удаляет отдельную тестовую схему. Последняя проверяет 100 пользователей с повторной подачей, 10 конкурирующих SQL-сессий, единственность lease, один активный update чата и общий лимитер. HTTP-тест 100 параллельных вызовов использует имитацию admission, поэтому не является измерением реальных RPS. Голос и Telegram в workflow имитируются; бизнес-права и транзакции выполняет настоящая SQL-база.
